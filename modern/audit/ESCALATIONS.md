# Escalation log

This is the escalation log that R7 — Anomaly handling (AAP 0.10) requires: every exception met in mechanical #1 work (an unexpected byte, width, sign or framing, or a contradiction between sources) is escalated to the #2 derive lane and recorded here, never normalised, defaulted or pattern-matched through. Each row's resolution is a proposal until the reviewer agrees with it under a9 (AAP 0.8.6). E29 is accepted only by its own signature row, `E29 — CP00 reply before write`, in `README.md`, never by the general escalation review. E30–E33 are refinement overrides and the only intended behaviour changes; every other row preserves, reproduces or declines to assert the audited COBOL behaviour. Halt IDs (H1–H6) refer to `HALTS.md`, and a case a row hands to a halt is blocked, with no parity assertion. Audit rows, rule modules and tests cite these IDs, so an ID is never renumbered or reused.

Status values:

- `PROPOSED`: resolution written, reviewer agreement pending.
- `AGREED — <reviewer>, <date>`: set only by the reviewer.
- `REJECTED — <reviewer>, <date>`: the resolution is reopened, and code that relies on it is revised before acceptance.
- `AWAITING SIGNATURE`: E29 only, until the `E29 — CP00 reply before write` row of `README.md` carries an `Accepted` decision with the reviewer's name and date. A `Rejected` signature reopens the CP00 ordering decision of AAP 0.3.4.2; it does not pass with a note.
