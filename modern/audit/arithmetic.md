# Arithmetic audit

This is the derive-lane (#2) audit of the COBOL statements that compute or move a financial value in the five in-scope programs that do money arithmetic: CBACT04C (interest, `intcalc`), COBIL00C (bill payment, endpoint 15), CBTRN02C (posting, `posttran`), COPAUA0C (authorization, CP00) and CBPAUP0C (purge, `cbpaup0j`). For each statement it records the receiving field, the value the COBOL stores and the Rust expression that reproduces it. It comes before `modern/crates/domain/src/money.rs` and `modern/crates/domain/tests/financial_parity.rs` (i2), and code that consumes it is accepted only once the reviewer marks this file `Accepted` in the status table of `README.md` (a8, a9; AAP 0.8.6). Every source was read in place at commit `59cc6c2` and none was changed (R16).

## The store rule

- Search, at `59cc6c2`: `grep -rniE 'ROUNDED|ON SIZE ERROR' app --include='*.cbl' --include='*.CBL'` matches nothing (exit status 1) across the 44 COBOL sources under `app/`; the same search over the copybooks matches nothing either.
- With no `ROUNDED` phrase, a fixed-point result is stored without rounding: digits beyond the receiver's scale are dropped, so the value is truncated toward zero at 0.01. With no `ON SIZE ERROR` phrase, IBM states that "truncation rules apply and the value of the affected resultant identifier is computed", and its alignment rules drop the integer digits a numeric `MOVE` receiver has no room for. Both drop high-order integer digits beyond the receiver's width and keep the sign: the stored value is the truncated value modulo 10^K, K being the receiver's integer digits.
- That is exactly `MoneyExpr::store::<K>()` (AAP 0.3.3.2): `RoundingStrategy::ToZero` at scale 2, then the integer part modulo 10^K, sign kept. A `MOVE` between money fields of different width is `MoneyExpr::from(x).store::<K>()`; a `MOVE` between fields of the same PIC copies the value. A comparison (`>`, `>=`, `<=`) compares exact values and stores nothing.
- Every row below obeys this rule, so every Rounding clause cell reads `none: truncate at the receiving PIC`. The one evaluation in these programs that does not truncate, `FUNCTION NUMVAL`, has no row here (see "Statements outside the table").

## Precision argument

This argument shows that `monthly_interest` computed with `rust_decimal::Decimal` stores the same value as the COBOL (ARITH-001). The reviewer checks each step.

1. Operands. `TRAN-CAT-BAL PIC S9(09)V99` has at most 11 digits at scale 2 and `DIS-INT-RATE PIC S9(04)V99` at most 6 at scale 2, so their product is exact at scale 4 with at most 17 digits, 13 of them integer. `Decimal` holds at least 28 significant digits, so it holds the product exactly.
2. COBOL intermediate (vendor rule). `dmax`, the largest number of decimal places among the receiver and the operands other than divisors, is 2. The quotient keeps the greater of (the dividend's decimal places − the divisor's) and `dmax`, that is max(4 − 0, 2) = 4, and the dividend's 13 integer places: 17 digits, within the 30-digit limit of `ARITH(COMPAT)`, the IBM-shipped default. The quotient is carried at 4 decimal places, the excess dropped, and then stored at 2. Dropping digits toward zero at the fourth place and then at the second gives the same value as dropping them at the second place of the exact quotient, because the first step keeps every digit the second reads.
3. Exact quotient. 1200 = 2⁴·3·5². Dividing the scale-4 product by 400 = 2⁴·5² terminates within 4 more places, at scale 8 or less. Dividing that by 3 either terminates or repeats one digit forever: every digit after the eighth decimal place is 3 (remainder 1) or 6 (remainder 2).
4. `Decimal` division. The quotient's magnitude is below 8.34 × 10⁹, so `Decimal` keeps at least 18 decimal places and, if the quotient does not terminate, rounds only at its last retained place, beyond the eighth, inside the repeating tail. Rounding a tail of 3s or 6s changes that last digit to 3, 4, 6 or 7 and never carries, because the tail never holds a 9. Truncating `Decimal`'s quotient at 0.01 therefore gives the same value as truncating the exact quotient.
5. Every other row is a `+`, a `−`, a `MOVE` or a comparison of scale-2 values with at most 13 digits. `Decimal` computes them exactly, so only the receiver's width can drop digits.

- `X-ARITH-1`
  - Found in: `COPAUA0C.cbl:376-379`; `COTRN02C.cbl:204-205,218-219,383-384,456-458`; `COACTUPC.cbl:1079-1080,1093,1107,1121,1135`; `CORPT00C.cbl:305-326`; AAP 0.3.3.2 and 0.8.3.
  - Anomaly class: request-vs-repository.
  - Finding: the AAP derives "every store truncates" from the absence of `ROUNDED` and `ON SIZE ERROR`. That holds for fixed-point evaluation only. IBM documents `NUMVAL` and `NUMVAL-C` as returning a floating-point approximation (long floating point under `ARITH(COMPAT)`, the IBM-shipped default, which the sample compile steps do not override), evaluates the whole expression in floating point, and rounds a floating-point value stored into a fixed-point receiver at the receiver's last digit. These COMPUTEs therefore round. For text with at most two decimal places and at most 15 significant digits the stored value is still the text's exact decimal value: long floating point carries at least 53 significant bits, so the approximation lies within 0.003 of that value, and rounding at 0.01 returns it. Were the conversion to truncate instead, `0.29`, whose nearest binary value is 0.28999…, would be stored as 0.28.
  - Proposed resolution: the replacement parses such text exactly as a decimal, with no floating point and no store (Money constraint, R1); within the bounds above this equals the COBOL's rounded value. Text outside them is X-ARITH-5. The rows belong to `messaging/COPAUA0C.md`, `online/COTRN02C.md`, `online/COACTUPC.md` and `online/CORPT00C.md`, which cite this candidate; this file has no row for these statements, so its rounding clause holds for every row it has.   - Path: the `NUMVAL` and `NUMVAL-C` COMPUTEs of X-ARITH-1, for text with more than two decimal places or more than 15 significant digits that their callers' edits let through: for example a CP00 amount token `1.005`, or a 16-digit card number at `COTRN02C.cbl:218-219`.

- `X-ARITH-6`, proposed as a new halt.
  - Path: `PIC S9(4) COMP` receivers whose result exceeds 9999 in magnitude: `ADD 1 TO PA-APPROVED-AUTH-CNT` and `PA-DECLINED-AUTH-CNT` at 9999 (`COPAUA0C.cbl:814,820`); `SUBTRACT 1` from them at −9999 (`CBPAUP0C.cbl:288,291`); `COMPUTE WS-DAY-DIFF` (`CBPAUP0C.cbl:47,282`) for a `YYDDD` difference beyond ±9999, that is an authorization roughly ten or more years old or one dated across a century rollover.
  - Why no single result: IBM makes the stored value depend on the `TRUNC` compiler option. Under `TRUNC(STD)`, the IBM-shipped default, the low four digits are kept, so 9999 + 1 stores 0 and a difference of 10001 stores 1; under `TRUNC(BIN)` the halfword keeps 10000 and 10001; under `TRUNC(OPT)` IBM leaves the result unpredictable. The sample compile steps (`samples/jcl/IMSMQCMP.jcl:37-38`, `samples/proc/BUILDBAT.prc:35-36`) set no `TRUNC` option, and no repository source records the installation default.
  - Bindings blocked: g3a and g3b, the beyond-9999 cases of ARITH-042 and ARITH-046; g3b, the expiry rows of `batch/CBPAUP0J.md` for such differences.
  - Escalation: none yet; the reviewer adds one to `ESCALATIONS.md` when folding the candidate in.
  - Candidate resolution: documentation of the deployed `TRUNC` option (the IBM-shipped default `TRUNC(STD)`, confirmed for the installation), or user descoping.
- `X-ARITH-7`, proposed as a new halt.
  - Path: every row whose Expected result names `store::<K>()`, in the case where the true result is negative and every digit the receiver keeps is zero, for example −1000000000.00 stored into `S9(09)V99`.
  - Why no single result: no digit survives to carry the sign.
