# CDRA / COACCT01 messaging audit

This is the derive-lane (#2) audit of COACCT01, the program behind the CDRA account inquiry over MQ. It records how a request is decoded and routed, the reply and error bodies byte by byte, their properties and the acknowledgement, and it comes before `modern/crates/domain/src/messaging/coacct01.rs`, `modern/crates/messaging/src/workers/cdra.rs` and the tests that prove them. Code that consumes it is accepted only once the reviewer marks this file `Accepted` in the status table of `modern/audit/README.md` (a8, a9; AAP 0.8.6). Every source was read in place at commit `59cc6c2` and none was changed (R16).

## Program and queues

- CDRA runs COACCT01: `DEFINE PROGRAM(COACCT01) … TRANSID(CDRA)` and `DEFINE TRANSACTION(CDRA) … PROGRAM(COACCT01)` (`CRDDEMOM.csd:1-5,17-18`). The program is the trigger-started server of the request/reply pair: it retrieves the MQ trigger message and serves the queue that message names.
- Replacement owners: `domain::messaging::coacct01` decodes the request with a total decoder and builds the reply and error bodies from the typed account record; `messaging::workers::cdra` runs the flow and reads the account through `persistence` (`AccountRepository::find_by_id`, R4); the consumption, publication, confirmation, acknowledgement and failure rules shared by the three workers are `messaging::broker` (AAP 0.3.4.2).
- Request queue: the COBOL takes it from the trigger message (`MOVE MQTM-QNAME TO INPUT-QUEUE-NAME`, `COACCT01.cbl:196-197`) and holds no literal for it. The replacement reads `CARDDEMO_QUEUE_REQUEST_ACCT`, default `CARD.DEMO.REQUEST.ACCT`.
- Reply and error queues are the COBOL literals `CARD.DEMO.REPLY.ACCT` (`COACCT01.cbl:198`) and `CARD.DEMO.ERROR` (`COACCT01.cbl:294`). The README's `CARDDEMO.REQUEST.QUEUE` and `CARDDEMO.RESPONSE.QUEUE` (`app/app-vsam-mq/README.md:53-54,71-72`) are not used (E01), and its message layouts (`app/app-vsam-mq/README.md:114-128`) are not followed: code is authoritative (E02, X-COACCT01-6).
- Account store: the CICS file `ACCTDAT ` (`LIT-ACCTFILENAME`, `COACCT01.cbl:115-116`) read `INTO(ACCOUNT-RECORD)`, the 300-byte `CVACT01Y` layout. The replacement reads table `accounts`, whose columns are the CVACT01Y rows of `copybooks.md`.

## Not carried over

These COBOL paths have no rule row, so a8 demands no test for them. Each has the reason given.

- `EXEC CICS RETRIEVE` of the trigger message and its failure branch, which moves `CICS RETREIVE` (sic) into `MQ-ERROR-PARA` and strings `RESP: `, the two response codes and `END` into `MQ-APPL-RETURN-MESSAGE`, including the self-move of `WS-CICS-RESP2-CD` (`COACCT01.cbl:191-210`; line 202, E17). The worker is a long-running AMQP consumer started by the operator, not a triggered CICS task, and its request queue comes from configuration. The codes the text embeds are halt H4 in any case.
- The `MQOPEN` paragraphs and their texts `INP MQOPEN ERR`, `OUT MQOPEN ERR` and `ERR MQOPEN ERR`, the last with its `DISPLAY` (`COACCT01.cbl:222-322`), and the `REPLY-QUEUE-OPEN` flag set when the input queue opens (line 245, E17). AMQP has no per-queue open: the seven queues are declared durable in `definitions.json`, and the worker checks them with a passive declare at start.
- `8000-TERMINATION` and the `MQCLOSE` paragraphs with their text `MQCLOSE ERR` (`COACCT01.cbl:538-619`), including the recursive `PERFORM 8000-TERMINATION` when closing the input or output queue fails (lines 572 and 594), the input queue's name reported for a failed close of the output queue (line 592), and the recursive `PERFORM 9000-ERROR` when closing the error queue fails (line 617, E17). AMQP has no per-queue close; a channel or connection is closed as a whole. The commit that the task-ending `EXEC CICS RETURN` (line 549) performs is stated in the failure rows (COACCT01-028, COACCT01-033, COACCT01-034).
- The `INP MQGET ERR:` path (`COACCT01.cbl:380-386`). It is replaced by the consumer-loss outcome of AAP 0.3.4.2: a tracing event, a reconnect with backoff, and the unacknowledged request redelivered by the broker and processed as a new one, with no error body. A reply confirmed just before the loss can therefore be sent twice, outside the single-delivery assumption of the parity tests. The one MQ cause of this path that an AMQP request could still present, a body over 1,000 bytes, is X-COACCT01-3 and X-COACCT01-H3.
- The five-second `MQGMO-WAITINTERVAL` with `MQGMO-WAIT`, and the task end on `MQRC-NO-MSG-AVAILABLE` (`COACCT01.cbl:337,350,377-378`). Replaced by `basic_get` polled every `CARDDEMO_MQ_POLL_MS` (default 250 ms) while the request queue is empty.
- The CICS task boundary and the `EXEC CICS SYNCPOINT` loop (`COACCT01.cbl:214-216,325-331`). RabbitMQ has no task boundary (as E14); the syncpoint's commit of a get with its put becomes the acknowledgement after a confirmed publish (COACCT01-026).
- Storage that no output reads: `QMGR-NAME` and `QUEUE-MESSAGE` (`COACCT01.cbl:93,105,180-183`), `WS-DATE-TIME` and its `INITIALIZE` (lines 35-38, 392), the `WS-CICS-RESP*` fields outside the retrieve branch (lines 26-30), and the counter `MQ-MSG-COUNT` (lines 54, 375), whose `ADD` is X-COACCT01-H4. The card-number and customer-ID parts of `WS-XREF-RID` (lines 121-125) are never filled (COACCT01-035).
- The CICS resource attributes of `CRDDEMOM.csd:1-8,17-26` beyond the CDRA ↔ COACCT01 pairing, including `DESCRIPTION(LIST CARDS)` (line 2), which describes neither program (X-CODATE01-6): they configure CICS and have no RabbitMQ counterpart. `STORAGECLEAR(NO)` (line 19) is cited only by X-COACCT01-H2.

## Request overrides

The request overrides the COBOL in two points that bind this flow, stated once here (AAP 0.3.4.2):

- Durability: every queue is durable, and every reply and error message is published persistent (`delivery_mode` 2).
- Acknowledgement: a request is acknowledged only after the publication it causes is confirmed (`Confirmation::Ack` with no returned message).

- Expected result: offsets are 0-based byte offsets into the message body, given with their length, and a range `a-b` includes both ends. Fixture values are never quoted: a row states a field's shape and the column it comes from.
- A row whose value halt H4 blocks says `HALTED(H4)` and asserts no value; a row that cites `halt H4` fixes only what the halt leaves assertable, such as an offset, and stays provable. A row whose case a halt candidate of this file names says one marker per candidate, `HALTED(X-COACCT01-H1)` or `HALTED(X-COACCT01-H2)` (`../README.md`, "Halts and escalations"), and asserts no parity value until the reviewer folds the candidate in or rejects it.

## Rules governing this file

- Cardholder Data Redaction: this file holds no card number, SSN, CVV or password and quotes no fixture account data. COACCT01-035 states that no CDRA reply, error body or worker trace carries a card number, an SSN in either form or an 8-byte password, from a store or from the requester: requester bytes reach a body only as the 4 function bytes of a decoded request (COACCT01-022). The not-found and bad-parameter replies carry eleven `*` in the key positions (COACCT01-021, COACCT01-022), and a body that does not decode is answered with `*` in every key and function position (COACCT01-003); in both the rule overrides the COBOL's echo (X-COACCT01-9).
- Typed Dates and Timestamps: the three date fields are `PicDate` values in the domain and `DATE` columns in the schema (CVACT01Y-006 to CVACT01Y-008); only their 10-byte rendering in the reply body is text (COACCT01-018), and that byte-level rendering is the codec's, which the rule exempts.
- Total Parsers Over Untrusted Input: the request decoder row (COACCT01-002) defines an outcome, a value or a typed error, for every input length and content, and `total_parsers.rs` tags it.
- R7 — Anomaly handling: every anomaly found is cited by its escalation ID or proposed below as `X-COACCT01-<n>`, never normalised or resolved by picking a value. The Equivalence failure constraint applies with it: the H4 rows and the cases the halt candidates name get no parity assertion.
- R16 — Authority and protected paths: `app/**` and `samples/**` are read only; this file is the only one written.
