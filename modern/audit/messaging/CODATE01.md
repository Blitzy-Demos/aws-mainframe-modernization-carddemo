# CDRD / CODATE01 messaging audit

This is the derive-lane (#2) audit of CODATE01, the program behind the CDRD system-date request over MQ. It records how a request is consumed, the reply and error bodies byte by byte, their properties and the acknowledgement, and it comes before `modern/crates/domain/src/messaging/codate01.rs`, `modern/crates/messaging/src/workers/cdrd.rs` and the tests that prove them. Code that consumes it is accepted only once the reviewer marks this file `Accepted` in the status table of `modern/audit/README.md` (a8, a9; AAP 0.8.6). Every source was read in place at commit `59cc6c2` and none was changed (R16).

## Program and queues

- CDRD runs CODATE01: `DEFINE PROGRAM(CODATE01) … TRANSID(CDRD)` and `DEFINE TRANSACTION(CDRD) … PROGRAM(CODATE01)` (`CRDDEMOM.csd:9-16,27-28`). The program is the trigger-started server of the request/reply pair: it retrieves the MQ trigger message and serves the queue that message names.
- Replacement owners: `domain::messaging::codate01` builds the reply and error bodies from a `Clock` reading; `messaging::workers::cdrd` runs the flow; the consumption, publication, confirmation, acknowledgement and failure rules shared by the three workers are `messaging::broker` (AAP 0.3.4.2).
- Request queue: the COBOL takes it from the trigger message (`MOVE MQTM-QNAME TO INPUT-QUEUE-NAME`, `CODATE01.cbl:140-146`) and holds no literal for it. The replacement reads `CARDDEMO_QUEUE_REQUEST_DATE`, default `CARD.DEMO.REQUEST.DATE`.
- Reply and error queues are the COBOL literals `CARD.DEMO.REPLY.DATE` (`CODATE01.cbl:147`) and `CARD.DEMO.ERROR` (`CODATE01.cbl:243`). The README's `CARDDEMO.REQUEST.QUEUE` and `CARDDEMO.RESPONSE.QUEUE` (`app/app-vsam-mq/README.md:53-54,71-72`) are not used (E01), and its message layouts (`app/app-vsam-mq/README.md:99-112`) are not followed (E02, X-CODATE01-6).

## Not carried over

These COBOL paths have no rule row, so a8 demands no test for them. Each has the reason given.

- `EXEC CICS RETRIEVE` of the trigger message and its failure branch, which moves `CICS RETRIEVE` into `MQ-ERROR-PARA` and strings `RESP: `, the two response codes and `END` into `MQ-APPL-RETURN-MESSAGE`, including the self-move of `WS-CICS-RESP2-CD` (`CODATE01.cbl:140-159`; line 151, E17). The worker is a long-running AMQP consumer started by the operator, not a triggered CICS task, and its request queue comes from configuration. The codes the text embeds are halt H4 in any case.
- The `MQOPEN` paragraphs and their texts `INP MQOPEN ERR`, `OUT MQOPEN ERR` and `ERR MQOPEN ERR`, the last with its `DISPLAY` (`CODATE01.cbl:171-271`). AMQP has no per-queue open: the seven queues are declared durable in `definitions.json`, and the worker checks them with a passive declare at start.
- The `MQCLOSE` paragraphs and their text `MQCLOSE ERR` (`CODATE01.cbl:442-523`), the `REPLY-QUEUE-OPEN` flag set when the input queue opens (line 194, E17), and the recursive `PERFORM 9000-ERROR` when closing the error queue fails (line 521, E17). AMQP has no per-queue close; a channel or connection is closed as a whole.
- The `INP MQGET ERR:` path (`CODATE01.cbl:329-336`). It is replaced by the consumer-loss outcome of AAP 0.3.4.2: a tracing event, a reconnect with backoff, and the unacknowledged request redelivered by the broker and processed as a new one, with no error body. A reply confirmed just before the loss can therefore be sent twice, outside the single-delivery assumption of the parity tests. The one MQ cause of this path that an AMQP request could still present, a body over 1,000 bytes, is X-CODATE01-3 and X-CODATE01-H1.
- The five-second `MQGMO-WAITINTERVAL` with `MQGMO-WAIT`, and the task end on `MQRC-NO-MSG-AVAILABLE` (`CODATE01.cbl:286,299,326-327`). Replaced by `basic_get` polled every `CARDDEMO_MQ_POLL_MS` (default 250 ms) while the request queue is empty.
- The CICS task boundary and the `EXEC CICS SYNCPOINT` loop (`CODATE01.cbl:163-167,274-280`). RabbitMQ has no task boundary (as E14); the syncpoint's commit of a get with its put becomes the acknowledgement after a confirmed publish (CODATE01-012).
- Storage that no output reads: `QMGR-NAME` and `QUEUE-MESSAGE` (`CODATE01.cbl:93,105,129-132`), `LIT-ACCTFILENAME`, `WS-RESP-CD` and `WS-REAS-CD` (lines 114-120), the `WS-CICS-RESP*` fields outside the retrieve branch (lines 26-30), and the counter `MQ-MSG-COUNT` (lines 54, 324), whose `ADD` is X-CODATE01-H2.
- The CICS resource attributes of `CRDDEMOM.csd:9-16,27-36` beyond the CDRD ↔ CODATE01 pairing: they configure CICS and have no RabbitMQ counterpart.

## Request overrides

The request overrides the COBOL in two points that bind this flow, stated once here (AAP 0.3.4.2):

- Durability: every queue is durable, and every reply and error message is published persistent (`delivery_mode` 2).
- Acknowledgement: a request is acknowledged only after the publication it causes is confirmed (`Confirmation::Ack` with no returned message).

## Reading the table

- Rule ID: `CODATE01-<nnn>` in flow order: the request (001–002), the reply body (003–009), the reply's properties and acknowledgement (010–013), the failure paths (014–019). Program is always `CODATE01`.
- Paragraph: the COBOL paragraph or paragraphs that perform the rule.
- Copybook field or PIC: the working-storage declaration as written, or the MQ descriptor field the program sets or reads.
- Expected result: offsets are 0-based byte offsets into the message body, given with their length, and a range `a-b` includes both ends. Literals in backticks are the exact bytes, case and spaces included; padding is stated as a count of spaces. Bodies are ASCII and carry no terminator.
- Time fields are compared by format only, never by value (AAP 0.5.6).
- A row whose value halt H4 blocks says `HALTED(H4)` and asserts no value; a row that cites `halt H4` fixes only what the halt leaves assertable, such as an offset, and stays provable.
- Source lines cite `CODATE01.cbl:<lines>`.

## Escalation candidates

Proposed under R7 — Anomaly handling. The reviewer folds each candidate into `ESCALATIONS.md` under the next free ID, as its `## Later entries` section describes; until then the rows above cite the candidate names.

- `X-CODATE01-1`
  - Found in: `app/app-vsam-mq/cbl/CODATE01.cbl:301-309,371-381,409-418`; AAP 0.3.4.2.
  - Anomaly class: request-vs-repository.
  - Finding: the reply and the error message reuse the descriptor the `MQGET` filled. `4100-PUT-REPLY` sets only `MQMD-MSGID`, `MQMD-CORRELID`, `MQMD-FORMAT` and `MQMD-CODEDCHARSETID`, and `9000-ERROR` only the last two, so `MQMD-PERSISTENCE`, `MQMD-EXPIRY` (the request's remaining lifetime, which IBM MQ returns on the get and applies afresh on the put), `MQMD-REPLYTOQ`, `MQMD-MSGTYPE` and the other descriptor fields are inherited from the request; `MQPMO-DEFAULT-CONTEXT` gives both puts the queue manager's default identity and origin context. A request's persistence and expiry therefore pass to its reply and to its error message. E16 settles the persistence and expiry of the CP00 reply only.
  - Proposed resolution: as AAP 0.3.4.2 fixes for CDRD: every reply and error message is persistent (`delivery_mode` 2, the request override) and carries no `expiration`; neither copies the request's `reply_to`, `type` or any property other than `message_id` and `correlation_id`, and no context property (`user_id`, `app_id`, `timestamp`) is set (CODATE01-010, CODATE01-011, CODATE01-018).
