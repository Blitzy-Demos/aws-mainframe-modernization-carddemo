# POSTTRAN audit: CBTRN02C, the daily transaction posting

This is the derive-lane (#2) audit of the batch job POSTTRAN and its program CBTRN02C, which the replacement runs as `carddemo-batch posttran`. It comes before `modern/crates/domain/src/batch/cbtrn02c.rs`, `modern/crates/batch/src/jobs/posttran.rs` and `modern/crates/batch/tests/posttran_i9.rs`, and code that consumes it is accepted only once the reviewer marks this file `Accepted` in the status table of `README.md` (a8, a9; AAP 0.8.6). No recorded COBOL output exists, so every expected result below is interpreted from the code, and audited defects are expected results (Behaviour constraint). Every source was read in place at commit `59cc6c2` and none was changed (R16).

## The job

- JCL: `STEP15` runs `CBTRN02C` with six files: `DALYTRAN`, the daily transaction file (`DISP=SHR`); `TRANFILE`, `XREFFILE`, `ACCTFILE` and `TCATBALF`, the transaction, cross-reference, account and category-balance KSDSs; and `DALYREJS`, the new generation `DALYREJS(+1)` with `DISP=(NEW,CATLG,DELETE)`, `RECFM=F` and `LRECL=430`.
- Replacement: subcommand `posttran` of `carddemo-batch`. Its option `--dalytran` names the input, default `../app/data/ASCII/dailytran.txt`, resolved against `modern/`, the working directory of every binary. It reads `card_xref`, `accounts` and `tran_cat_balances`; inserts into `transactions`; updates `accounts`; inserts and updates `tran_cat_balances` (migrations 0001 and 0002); and writes the reject generation `DALYREJS.G<nnnn>` in `Config::dalyrejs_dir()` (`CARDDEMO_VAR_DIR`/`dalyrejs`, default `./var/dalyrejs`) through `runtime::gdg::next_generation`: 430-byte records, each followed by LF, with the file's path printed to standard output. It runs against a database that `carddemo-migrate` has migrated and the loads of `batch/LOADS.md` have filled, and never migrates (Single Schema Executor).
- Today: `FUNCTION CURRENT-DATE`, read once per posted record (CBTRN02C-013). Replacement: the injected `Clock`; tests use `FixedClock`, and `fixtures.md` uses the instant `2022-07-01 12:00:00.000000`.
- Job log: each `DISPLAY` writes one line to SYSOUT. Replacement: one tracing event per line (CBTRN02C-034, X-POSTTRAN-4).

## Rules governing this file

- Cardholder Data Redaction: `DALYTRAN-CARD-NUM`, `XREF-CARD-NUM` and `TRAN-CARD-NUM` are named, never quoted, and no card number or other run of 16 digits appears here. The reject records and `transactions.card_num` hold full card numbers, as the COBOL writes them; they are a local file and a table, not egress. No job-log event, span or error carries a card number or a record's bytes (CBTRN02C-037).
- Typed Dates and Timestamps: the expiry test compares `accounts.acct_expiraion_date` (`DATE`) with the date of `DALYTRAN-ORIG-TS` as typed values (CBTRN02C-010), and `TRAN-ORIG-TS` and `TRAN-PROC-TS` are stored as `TIMESTAMP(6)` with their layout codes (CBTRN02C-012, CBTRN02C-013). The 350 input bytes of a reject record are codec-level bytes, which the rule excludes (CBTRN02C-027).
- Checked Integer Narrowing: both counters are `PIC 9(09)`; overflowing one needs a run of more than 999,999,999 records, which no binding reaches (CBTRN02C-036). Every money store cites its `ARITH-` row.
- Money constraint and R1: amounts appear only through ARITH-023 to ARITH-033; nothing here involves floating point.
- Local-Only Runtime: the reject generation is a local file under `CARDDEMO_VAR_DIR`, and the job needs only PostgreSQL.
- Behaviour constraint: E09, E10, ARITH-033, X-FIXTURES-1, the reason `0109` that has no effect (CBTRN02C-023) and the close-status defect (CBTRN02C-040) are expected results, reproduced and never fixed.
- R7 — Anomaly handling: anomalies are cited by escalation ID or proposed below as `X-POSTTRAN-<n>` and `X-POSTTRAN-H<n>`, never normalised. R16: `app/**` is read only.

## Escalation candidates

Proposed under R7 — Anomaly handling. The reviewer folds each candidate into `ESCALATIONS.md` under the next free ID, as its `## Later entries` section describes; until then the rows above cite the candidate names.

- `X-POSTTRAN-1`
  - Found in: `app/cbl/CBTRN02C.cbl:440-442,467-579,707-711`; AAP 0.3.3.4, which states the one-transaction rule for the loads; AAP 0.3.4.3.
  - Anomaly class: request-vs-repository.
  - Finding: CBTRN02C updates three VSAM files for each posted record, the category balance, the account and then the transaction file, and VSAM keeps every completed write. A failed transaction write (CBTRN02C-025), or any later failure, abends the step with that record's category balance and account already changed and every earlier record's effects in place. A replacement that ran a record, or the whole job, inside one PostgreSQL transaction would undo those writes on failure and leave a state the COBOL never leaves.
  - Proposed resolution: reproduced (Behaviour constraint): `posttran` issues each write as its own committed statement, in program order, and never wraps them (CBTRN02C-015). A run that fails part way leaves the tables as CBTRN02C leaves its files, and a rerun meets X-POSTTRAN-H1, as on the mainframe.
