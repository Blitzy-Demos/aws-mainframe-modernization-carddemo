# TRANREPT audit: CBTRN03C, the transaction detail report

This is the derive-lane (#2) audit of the batch job TRANREPT, its unload and SORT steps and its program CBTRN03C, which the replacement runs as `carddemo-batch tranrept`. It comes before `modern/crates/domain/src/batch/cbtrn03c.rs`, `modern/crates/batch/src/jobs/tranrept.rs` and `modern/crates/batch/tests/tranrept.rs`, and code that consumes it is accepted only once the reviewer marks this file `Accepted` in the status table of `../README.md` (a8, a9; AAP 0.8.6). Every source was read in place at commit `59cc6c2` and none was changed (R16). Audited defects are expected results (Behaviour constraint).

## The job

- JCL: three steps (`TRANREPT.jcl:23-80`). The first, `STEP05R`, runs the `REPROC` procedure, an IDCAMS `REPRO` of the transaction KSDS into `TRANSACT.BKUP(+1)`. The second, also named `STEP05R`, sorts that unload into `TRANSACT.DALY(+1)` with an `INCLUDE` on the processing date and `SORT FIELDS=(TRAN-CARD-NUM,A)`. `STEP10R` runs CBTRN03C over the sorted file, the cross-reference, type and category KSDSs and the `DATEPARM` dataset, writing `TRANREPT(+1)` (`LRECL=133,RECFM=FB`).
- Replacement: subcommand `tranrept` of `carddemo-batch`, with options `--start-date` and `--end-date`, defaulting to `2022-01-01` and `2022-07-06`, the `PARM-START-DATE` and `PARM-END-DATE` constants of `TRANREPT.jcl:43-44`. It reads `transactions`, `card_xref`, `transaction_types` and `transaction_categories`, the last two being the VSAM data version (E23), and never schema `db2`. It writes no table and one file: `TRANREPT.G<nnnn>` in the reports directory (`CARDDEMO_VAR_DIR` joined with `reports`, default `./var/reports`), generation (+1) by `runtime::gdg`, 133-byte records each followed by LF, its path printed on standard output (AAP 0.3.4.3).
- Selection follows the stored processing timestamp. `posttran` stamps `TRAN-PROC-TS` from the injected `Clock` (layout `D`, PIC-019), so a run reports only what was posted on a date inside the window. Tests run `posttran` under a `FixedClock` inside the window, as the POSTED scenario of `../fixtures.md` does (`2022-07-01`), or pass dates that cover the stamped date.
- Job log: each `DISPLAY` becomes one line of standard output, in program order, as `CBPAUP0J.md` defines SYSOUT. The replacement departs from the displayed bytes only where Cardholder Data Redaction requires it: the `TRAN-RECORD` line shows its six free-text fields as `*`, whatever they hold, and its card number in the redacted form, and the cross-reference failure shows the card number in the redacted form (CBTRN03C-012, CBTRN03C-014; X-TRANREPT-3).

## How the rows are proved

- `modern/crates/batch/tests/tranrept.rs` runs the `carddemo-batch tranrept` binary as a subprocess against a testcontainers PostgreSQL migrated through `runtime::migrate` (`test_support::postgres`) and loaded by the nine loads, after a `carddemo-batch posttran` run over `dailytran.txt`. Both binaries read the system clock, which no `FixedClock` replaces across the process boundary, so the runs over POSTED take a window from the day before today to the day after; only the default-window test reproduces the POSTED `FixedClock` instant, by copying `posttran`'s rows into a freshly loaded database through `TransactionRepository::insert` with that processing timestamp (FIXPOST-901). It asserts the generation file byte for byte, the printed path, the job-log lines and the exit status, and carries `// audit: CBTRN03C-<nnn>` for each row it proves; FIXRPT supplies the per-record values over POSTED.
- The pure rules (the option parse, the DATEPARM record, the record layouts, the editing, the page-break and end-of-file sequences and the dead path of CBTRN03C-011) are also tagged in `modern/crates/domain/tests/batch_rules.rs`, which drives `domain::batch::cbtrn03c` with records no fixture holds.
- The not-found rows (CBTRN03C-014, CBTRN03C-016, CBTRN03C-018) are proved in `modern/crates/domain/tests/batch_rules.rs` with a transaction whose card, type or category the lookups lack, and CBTRN03C-014 also by the job's unit test `a_missing_cross_reference_abends_the_run` in `modern/crates/batch/src/jobs/tranrept.rs`. The job runs as a subprocess, which no repository double reaches, so `tranrept.rs` provokes the failure rows from outside the process: a regular file where the `reports` directory belongs, so the open of `REPTFILE` fails (CBTRN03C-007); a TCP `Relay` between the job and the container that closes the selection's connection after its first row, so the next fetch fails inside the loop (CBTRN03C-010, which the job's unit tests also prove over a row source whose second fetch fails); and a `ulimit -f` file-size limit that `/bin/sh` sets before it runs the binary, below the first buffer the job writes, so a write inside the loop fails (CBTRN03C-033), or above every buffer the loop writes, so the last write, at the close, fails (CBTRN03C-034). The lookup failures other than `INVALID KEY` (CBTRN03C-040, CBTRN03C-041, CBTRN03C-042) are provoked by the same `Relay` closing a lookup table's connection at its row description, not through a missing row, and are reported `BLOCKED` with no parity assertion (X-TRANREPT-H5). No fixture is edited or copied.
- CBTRN03C-039 is checked over every `tranrept` run of the suite: `assert_no_fixture_card_number` searches the run's standard output and standard error whole, every tracing event included, for the 50 fixture card numbers that `test_support::fixtures::fixture_card_numbers` reads, and one run's transaction IDs are themselves card numbers.
- A row that names a halt candidate is reported blocked for the case the candidate names, with no parity assertion for it, until the reviewer folds the candidate in or rejects it; the rest of the row stays provable.

## Rules governing this file

- Cardholder Data Redaction: report records carry no card number (CBTRN03C-023), so the report holds none. The job-log lines that show `TRAN-RECORD` or a card number render the redacted form, and the `TRAN-RECORD` line shows the record's free-text fields, unvalidated text that can carry a card number, an SSN or a password, as `*` whatever they hold (CBTRN03C-012, CBTRN03C-014, CBTRN03C-039). - Money constraint and R1: the three totals are `Money<9>` stored by `store::<9>()` (CBTRN03C-028); nothing involves floating point.
- Local-Only Runtime: the report is a local file (CBTRN03C-032); nothing goes to a printer, a spool or object storage.
