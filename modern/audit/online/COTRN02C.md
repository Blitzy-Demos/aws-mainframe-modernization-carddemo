# COTRN02C — transaction add (CT02, endpoint 13)

This is the derive-lane (#2) audit of `COTRN02C` (`app/cbl/COTRN02C.cbl`, 783 lines), the CICS program behind transaction `CT02`, map `COTRN2A` of mapset `COTRN02`, main-menu option 08 of `COMEN01C`. It adds one record to the `TRANSACT` file. The replacement serves it as endpoint 13, `POST /api/v1/transactions`, which takes `TranAddRequest { aid, acct_id?, card_num?, fields, confirm }` and returns `TranAddResult` (the filled-in key, the data fields as the screen then shows them, copied ones included, the message and the new transaction ID) or `ScreenError { message, field? }` (AAP 0.3.4.1), and as the screen `COTRN02` at route `/transactions/add`. The file comes before `crates/domain/src/online/cotrn02c.rs`, `crates/api/src/{services,dto,handlers}/cotrn02c.rs`, the endpoint-13 cases of `crates/api/tests/endpoints_transactions.rs` and `frontend/src/screens/COTRN02.tsx`, and code that consumes it is accepted only once the reviewer marks it `Accepted` in the status table of `modern/audit/README.md` (a8, a9; AAP 0.8.6). Every source was read in place at commit `59cc6c2` and none was changed (R16).

## Reading the table

- Rule ID: `COTRN02C-<nnn>`, in the order the program runs: entry and keys (001-008), the key-field edits and cross-reference reads (009-019), the data-field edits (020-039), the confirmation (040-042), the add (043-051), the copy of PF5 (052-056), then what the response and the screen carry (057-060); COTRN02C-061, the token check that stands for the COMMAREA test of COTRN02C-001, comes last.
- Input condition: the request (`aid`, `acct_id`, `card_num`, `fields`, `confirm`) and the stored state it meets. Blank means absent, empty or all spaces, which stands for the COBOL's `SPACES` or `LOW-VALUES`. A value shorter than its map field is padded on the right with spaces to the map width, as BMS delivers it, so "n digits" means exactly n ASCII digits: a shorter value fails the COBOL `NUMERIC` class test on its padding.
- The data-field rows (COTRN02C-020 to COTRN02C-039) apply in table order. Each assumes the key resolved (COTRN02C-012 or COTRN02C-017) and every earlier data-field row passed, because the first failing edit ends the request (COTRN02C-008). On PF5 they judge the copied fields (COTRN02C-054).
- Expected result: the HTTP status and body, the field the screen focuses, and the store effects. `200` returns `TranAddResult`; `400`, `404` and `500` return `ScreenError` with the exact literal the program moves to `WS-MESSAGE`. The program's cursor (the field's length `L` set to −1) becomes `field`: `acct_id`, `card_num` or `confirm`, or, for a data field, the member of `fields` that carries the map field the row names (`TTYPCD`, `TCATCD`, `TRNSRC`, `TDESC`, `TRNAMT`, `TORIGDT`, `TPROCDT`, `MID`, `MNAME`, `MCITY`, `MZIP`); the DTO module fixes the member names.
- One pseudo-conversational task is one request. `SEND-TRNADD-SCREEN` ends with `EXEC CICS RETURN`, so the first message the program sets is the response and nothing after it runs (COTRN02C-008).
- Layer: `server` rows are observable through endpoint 13, `client` rows send no request, as `README.md` defines them. The map lengths, which the zod schema and the request DTO both enforce, are the `both` rows `COTRN02-013`, `COTRN02-017`, `COTRN02-021`, `COTRN02-024`, `COTRN02-027`, `COTRN02-030`, `COTRN02-033`, `COTRN02-036`, `COTRN02-039`, `COTRN02-045`, `COTRN02-048`, `COTRN02-051`, `COTRN02-054` and `COTRN02-057` of `screens.md`. No edit of this program is repeated by the schema, so every edit row here is `server` (see the first rule below).

## Rules governing this file

- Layer of the edits (Behaviour constraint): the data-field edits run only after the cross-reference read, whose not-found and lookup messages no screen can predict. A zod check that rejected an empty or malformed data field before sending would show its own message where the COBOL shows the read's, and so break the program's first-message order. The key-field edits precede every read, but the schema repeats none of them either, as `online/CSUTLDTC.md` already states for the `COTRN02` schema (map lengths only): the request is always sent, and the server's message always governs.
- Cardholder Data Redaction: endpoint 13 returns a card number only in its redacted form, twelve `*` followed by the last four digits, whether the user typed it or the program filled it from the cross-reference (COTRN02C-012, COTRN02C-017, E32). The full number reaches only `transactions.card_num` (CVTRA05Y-011, PIC-024). This file quotes no card number, account number or transaction ID from the fixtures.
- Typed Dates and Timestamps: `TORIGDT` and `TPROCDT` enter as raw text, the input to COTRN02C's date edits (the raw-edit-input exception of AAP 0.3.4.1; `screens.md` COTRN02-036 and COTRN02-039). Once the edits accept them they are typed: the response carries them as typed dates, and the stored `orig_ts` and `proc_ts` are `TIMESTAMP(6)` values with layout code `S` (COTRN02C-046, PIC-020, E33).
- Equivalence failure: date validity is `CEEDAYS`'s (halt H5). Rows marked `HALTED(H5)` assert nothing; rows that cite `halt H5` hold for every verdict that accepts both dates and are reached in tests by substituting that verdict, as `online/CSUTLDTC.md` describes.
- Money constraint: the amount travels as the 12-character string of `WS-TRAN-AMT-E PIC +99999999.99`, and its stored value is the decimal value of the edited text (X-ARITH-1), parsed with no floating point; no row implies floating point.
- Behaviour constraint and R7 — Anomaly handling: the program's quirks are expected results, among them that the account file is never read and the account ID never stored, and that PF5 copies the highest-ID transaction of the whole file. Anomalies and cases with no single result are proposed below the table, never smoothed over.
- Thin Request Handlers: every outcome in the table is decided by `domain::online::cotrn02c` and carried out by `api::services::cotrn02c`; the handler only extracts, calls the service and maps.
- Bounded Pagination: endpoint 13 returns a single resource and takes no page size.
- R16 — Authority and protected paths: markdown under `modern/audit/` only.

## How the rows are proved

- `server` rows: `crates/api/tests/endpoints_transactions.rs` (g1b), over a migrated, fixture-loaded database with a `U` token (and an `A` token for COTRN02C-003) and a `FixedClock`. Each test carries `// audit: COTRN02C-<nnn>`. Rule functions may also be tested in `crates/domain/tests/online_rules.rs`.
- The nine loads leave `transactions` empty, so every test of the add or of PF5 first posts (`posttran`) or inserts transactions; the empty table is halt candidate X-COTRN02C-H1.
- Card-path tests use fixture cards whose number is at most 2⁵³; a larger card number is X-ARITH-5 (COTRN02C-016).
- `client` rows: `frontend/src/screens/COTRN02.test.tsx` (Vitest) and, for the transfers, `frontend/e2e/nav.spec.ts`.
- A `HALTED` row, or a row that hands part of its input to a halt or a halt candidate, keeps its tags; its test reports that case `BLOCKED` and asserts no parity value until the reviewer resolves it.
