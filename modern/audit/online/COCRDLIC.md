# COCRDLIC audit: the card list (CCLI, endpoint 7)

This is the derive-lane (#2) audit of `COCRDLIC`, the CICS program behind transaction `CCLI` and map `COCRDLI` (`CCRDLIA`), route `/cards`. Its rows are the expected results of `modern/crates/domain/src/online/cocrdlic.rs`, `modern/crates/api/src/services/cocrdlic.rs`, the card page query in `modern/crates/persistence/queries/`, `modern/crates/api/src/{dto,handlers}/cocrdlic.rs`, `modern/crates/api/tests/endpoints_cards.rs` and the `COCRDLI` screen, which are accepted only once the reviewer marks this file `Accepted` in the status table of `modern/audit/README.md` (a9). The COBOL is read in place and never modified (R16).

The program is served by endpoint 7, `GET /api/v1/cards`: `CardListQuery { acct_id?, card_num?, page_key?, direction?, page_size? }` → `CardListResponse`, up to seven rows of `{ card_ref, card_num (masked), acct_id, status }`, the page number, and the first and last keys of the page as `card_ref` values, with the screen's error line (`ERRMSG`) and information line (`INFOMSG`). Every request needs a verified token; the endpoint has no admin gate (COCRDLIC-001). The row selections `S` and `U` never reach it: they only navigate, to `/cards/view` or `/cards/update`, carrying the row's `acct_id` and `card_ref` in route state (AAP 0.3.4.1), so the selection edit is a screen rule.

The default page size is seven, the program's screen size (`WS-MAX-SCREEN-LINES`, `COCRDLIC.cbl:177-178`), and every row below is stated for it. `page_size`, an integer from 1 to 100 whose out-of-range values are rejected, is a Bounded Pagination rule rather than a COBOL one; it is proved by `modern/crates/api/tests/pagination.rs`, no row here covers it, and the screen never sends it.

## Reading the table

- Paging state. The program keeps, between interactions, `WS-THIS-PROGCOMMAREA` (`COCRDLIC.cbl:229-260`) after the COMMAREA: the first key (`WS-CA-FIRST-CARD-NUM`), the last key (`WS-CA-LAST-CARD-NUM`), the page number (`WS-CA-SCREEN-NUM PIC 9(1)`), the last-page flag (`WS-CA-LAST-PAGE-DISPLAYED`), the next-page indicator (`WS-CA-NEXT-PAGE-IND`) and the seven displayed rows (`WS-SCREEN-DATA`). `WS-SCREEN-DATA` is declared at level 05 after level-10 items; by the COBOL level-number rule (IBM Enterprise COBOL Language Reference) it is a member of `WS-THIS-PROGCOMMAREA` like them, so the displayed rows travel in the COMMAREA, which the transfer of COCRDLIC-015 relies on. Rows state results in terms of this state; X-COCRDLIC-2 proposes how endpoint 7 carries it.
- Requests. ENTER sends the displayed page's first key as `page_key` with no direction; F7 sends the first key with direction backward; F8 sends the last key with direction forward; a fresh start sends no `page_key`. A "matching card" is one that passes the filters of COCRDLIC-010.
- Order. Cards are read in ascending card-number order, the key order of the `CARDDAT` KSDS; every card number has 16 digits, so the database's text order is the same.
- Messages are quoted exactly as the program moves them. The error line is `WS-ERROR-MSG PIC X(75)` moved to `ERRMSGO PIC X(78)`; the information line is `WS-INFO-MSG PIC X(45)` moved to `INFOMSGO PIC X(45)`.
- Status. A list result is 200 with its rows and messages, `'NO RECORDS FOUND FOR THIS SEARCH CONDITION.'` included: the program renders the empty page with its filters and page number, which a `ScreenError` cannot carry, and an empty search is a page of the collection rather than a missing resource. A filter edit is 400 with its field; a store failure is 500. A missing or invalid token is 401 (AAP 0.3.4.1); no 403 arises, as the endpoint has no admin gate.
- Fixture. `app/data/ASCII/carddata.txt` holds 50 cards in card-number order, one per account, every status `Y`: without a filter the list has eight pages, seven of seven cards and one of one. Fixture cards are cited by line (`carddata.txt:n`), never by number.

## How the rows are proved

- `server`: `modern/crates/api/tests/endpoints_cards.rs`, over the fixture-loaded database, asserting status, rows, keys, page number and both message lines. Cases the fixture cannot produce (several cards per account, a read-ahead that finds a card the filter excludes, more than 63 cards for the page-number wrap) add cards to the test database.
- `both`: the server half in `endpoints_cards.rs` (status, message and field); the client half in `modern/frontend/src/schemas/COCRDLI.test.ts` (the screen's zod schema rejects the same input with the same message).
- `client`: `modern/frontend/src/screens/COCRDLI.test.tsx` (selection edits, rendering, attributes, filter echo), `modern/frontend/src/lib/pfkeys.test.ts` (COCRDLIC-003) and `modern/frontend/e2e/nav.spec.ts` (COCRDLIC-002, COCRDLIC-004, COCRDLIC-015).
- A `HALTED` row keeps its tags; its test reports it `BLOCKED` and asserts no value. Until the reviewer folds a halt candidate in, no parity assertion is written for what it names.
- The filter edits are `both`: the screen repeats them, so a filter error sends no request and keeps the displayed page, as the program, which reads nothing on a filter error, does (COCRDLIC-011).

## Rules governing this file

- Cardholder Data Redaction (E32): list rows and page keys carry `card_ref` and the card number redacted to twelve `*` followed by its last four digits, never the full number, although the COBOL shows it in full (COCRDLIC-032). This file quotes no card number.
- Bounded Pagination: the default page size of seven is recorded above; the page-size rejection is not a COBOL rule and has no row here.
- Equivalence failure constraint and H4: the CICS `RESP` and `RESP2` codes strung into the file-error text are blocked (COCRDLIC-037, X-COCRDLIC-H1); the filter-error rows COCRDLIC-006, COCRDLIC-008 and COCRDLIC-009 assert nothing (X-COCRDLIC-H2).
- Behaviour constraint and R7 — Anomaly handling: the program's paging defects are the expected results of their rows, never corrected (X-COCRDLIC-3); anomalies are proposed after the table.
- Typed Dates and Timestamps: the list carries no date field.
- R16 — Authority and protected paths: `app/**` and `samples/**` are read only; this file is the only one written.

## Escalation candidates

- `X-COCRDLIC-1`
  - Found in: `app/cbl/COCRDLIC.cbl:4-7,315-325,388,462-466,522,550`.
  - Anomaly class: declaration-not-followed.
  - Finding: the header says the program lists all cards for an admin user with no context and only the COMMAREA account's cards for any other user. The code never reads `CDEMO-USER-TYPE`, so every caller lists every card. It also overwrites the COMMAREA identity: it sets `CDEMO-USRTYP-USER` at every re-initialisation and before every transfer, and the F3 return path's `INITIALIZE CARDDEMO-COMMAREA` clears `CDEMO-USER-ID`. A `CCLI` start with no COMMAREA lists the cards with no sign-on at all.
  - Proposed resolution: the code is authoritative for the listing (COCRDLIC-001): no account restriction and no admin gate. Endpoint 7, like every endpoint but sign-on, requires a verified token and answers 401 without one (AAP 0.3.4.1, n5), and identity comes only from that token (AAP 0.5.1). The COMMAREA overwrites are therefore not reproduced: the user type that reaches `/cards/view` (where endpoint 8's disclosure depends on it, AAP 0.3.4.8), `/cards/update` and `/menu` is the token's.
- `X-COCRDLIC-2`
