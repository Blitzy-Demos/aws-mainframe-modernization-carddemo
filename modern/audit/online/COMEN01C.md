# COMEN01C — main menu (CM00, endpoint 2)

This is the derive-lane (#2) audit of `app/cbl/COMEN01C.cbl` (308 lines), the main menu for regular users: transaction `CM00`, map `COMEN01` (`COMEN1A`), route `/menu`. Its replacement is endpoint 2, `GET /api/v1/menus/main` → `MenuResponse`, which returns the fixed option table of `COMEN02Y` with per-option admin-only and installed flags and the program's rejection texts. ENTER's option checks are served from that response on the screen, with no further request (AAP 0.3.4.1). The rows come before `crates/domain/src/online/comen01c.rs`, `crates/api/src/services/comen01c.rs`, `crates/api/src/{dto,handlers}/comen01c.rs`, the menu cases of `crates/api/tests/endpoints_signon_menus.rs` and `crates/api/tests/auth_gate.rs`, and `frontend/src/screens/COMEN01.tsx`. Code that consumes them is accepted only once this file is `Accepted` in the status table of `modern/audit/README.md` (a8, a9). The COBOL was read in place at commit `59cc6c2` and not changed (R16).

## Reading the table

- Rule ID: `COMEN01C-<nnn>`, in paragraph order: `MAIN-PARA`, `PROCESS-ENTER-KEY`, `SEND-MENU-SCREEN` with `POPULATE-HEADER-INFO`, then `BUILD-MENU-OPTIONS`. A `server` row that states what endpoint 2 returns sits at the paragraph whose literal or table it reproduces.
- Paragraph: `A → B` names the paragraph `A` performs.
- Input condition: the AID key and the screen state as COMEN01C sees them, or, for a `server` row, the request to endpoint 2. "Option" is the 2-digit value the edit of `COMEN01C-008` produces from the option input.
- Expected result: literals exactly as the program moves them, in single quotes with their spacing; for a `server` row the values of `MenuResponse`; for a `client` row what the screen shows and where it navigates. Only the screen load calls endpoint 2, so the only statuses are 200 and the 401 of `COMEN01C-002`; the program's messages travel inside `MenuResponse` and are shown by the screen, never returned as a `ScreenError`.
- Layer: `server` for what endpoint 2 returns; `client` for the ENTER edit, the checks the screen applies with the response, every transfer and what the screen renders. No row is `both`: the option input is never sent (`COMEN01-025`), so no request DTO revalidates it.

## Rules governing this file

- Bounded Pagination: the menu is a single resource, the fixed 11-entry table of `COMEN02Y`, not a collection. Endpoint 2 takes no `page_size`, so the page-size rejection of that rule never applies (`COMEN01C-004`; AAP 0.3.4.1).
- Identity and Trust (AAP 0.5.1): the user type the admin-only check compares is the verified token's `usr_type` claim, the `CDEMO-USER-TYPE` sign-on set (`COSGN00C-014`), never a request field (`COMEN01C-004`, `COMEN01C-012`).
- Thin Request Handlers: the table, flags and texts come from `domain::online::comen01c` through `api::services::comen01c`; the handler only extracts `SignedOnUser`, calls the service and maps the result.
- Cardholder Data Redaction: endpoint 2 returns no card number, SSN, CVV or password, and this file quotes none.
- Messages and HTTP status (`README.md` of the audit): 200 and 401 only, and no row carries another status.
- Behaviour constraint and R7 — Anomaly handling: the unreachable branches and the uneven `STRING` delimiters are recorded as expected results, never smoothed over; the anomalies found are proposed after the table as `X-COMEN01C-<n>`. R16 — Authority and protected paths: `app/**` is read only.
