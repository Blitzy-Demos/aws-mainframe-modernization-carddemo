# COPAUS2C — fraud recorder (CPVD PF5, store half of endpoint 23)

This is the derive-lane (#2) audit of COPAUS2C, "Mark Authorization Message Fraud", a 244-line CICS COBOL Db2 program. It comes before `modern/crates/domain/src/online/copaus2c.rs`, the `auth_fraud` repository in `modern/crates/persistence` and `modern/crates/api/tests/endpoints_authorizations.rs`, and code that consumes it is accepted only once the reviewer marks this file `Accepted` in the status table of `modern/audit/README.md` (a8, a9; AAP 0.8.6). Every source was read in place at commit `59cc6c2` and none was changed (R16).

- COPAUS2C has no transaction of its own. It runs only under `EXEC CICS LINK` from COPAUS1C's `MARK-AUTH-FRAUD`, the PF5 key of CPVD, with COPAUS1C's 272-byte `WS-FRAUD-DATA` as COMMAREA: the account ID `9(11)`, the customer ID `9(9)`, the 200-byte `CIPAUDTY` detail as COPAUS1C read it with the fraud flag already flipped, `WS-FRD-ACTION` (`F` report, `R` remove), and the two outputs `WS-FRD-UPDATE-STATUS` (`S` success, `F` failure) and `WS-FRD-ACT-MSG PIC X(50)`.
- Endpoint 23, `POST /api/v1/authorizations/{acct_id}/{auth_key}/fraud`, belongs to COPAUS1C (AAP 0.3.4.1). This file covers its store half: the `auth_fraud` row and the status and message COPAUS2C hands back. `modern/audit/online/COPAUS1C.md` holds the key handling, the detail replace, the commit or rollback and the success messages, and its PF5 rows cite these IDs.
- Table `auth_fraud` (migration `0004_authorizations.sql`) keeps the Db2 columns in DDL order: `CHAR(n)` texts, `NUMERIC(12,2)` amounts, `SMALLINT` `pos_entry_mode`, `VARCHAR(22)` `merchant_name`, `auth_ts TIMESTAMP(6)`, `fraud_rpt_date DATE`, and `acct_id` and `cust_id` as `BIGINT` with their digit ranges. Primary key `(card_num, auth_ts)` from `AUTHFRDS.ddl:2-3,28`; unique index `xauthfrd (card_num ASC, auth_ts DESC)` from `XAUTHFRD.ddl:1-4`.
- The rules live in `domain::online::copaus2c`, and the insert and update in the `auth_fraud` repository; the endpoint's service calls both inside COPAUS1C's transaction.

## Reading the table

- Rule ID: `COPAUS2C-<nnn>`, in source order. Program: always COPAUS2C. Paragraph: the paragraph that holds the statement.
- Copybook field or PIC: the declaration as written, COBOL spellings included; DCLGEN host variables come from `AUTHFRDS.dcl`.
- Expected result: the effect on the COMMAREA and on `auth_fraud`, messages exactly as moved (quoted literals keep their leading spaces), and the HTTP status endpoint 23 returns: 200 when COPAUS2C succeeds and COPAUS1C commits, 500 for a database failure. No other status arises from this program. The 200 is COPAUS1C-032's success branch, HALTED(X-COPAUS1C-H2) in `modern/audit/online/COPAUS1C.md`, so no row here asserts it, or anything committed with it, as a parity result; the 500s and their rollbacks stay assertable.
- Layer: every row is `server`. COPAUS2C has no screen, and each rule is observable through endpoint 23: its status and message, the writes its transaction issues, or the contents of `auth_fraud`; "How the rows are proved" below says what the halt of COPAUS1C-032 leaves assertable.
- Time: every date and time comes from the injected `Clock`; tests use `FixedClock` and compare time-dependent values by format and type (AAP 0.5.6).

## Rules governing this file

- Cardholder Data Redaction: the file holds no card number value. COPAUS2C-013 states where the full number goes and that no message carries it.
- Typed Dates and Timestamps: `auth_fraud.auth_ts` and `auth_fraud.fraud_rpt_date` are typed (`TIMESTAMP(6)` and `DATE`) in the schema, the row type and the domain model (COPAUS2C-004, COPAUS2C-007). The COMMAREA's `PA-FRAUD-RPT-DATE` stays `X(08)` text in `pending_auth_details` (CIPAUDTY-027).
- Equivalence failure constraint and halt H3: the `SQLCODE` and `SQLSTATE` values in the two error texts are Db2's and assert nothing (`HALTED(H3)`, X-COPAUS2C-H1). Endpoint 23's committed success is HALTED(X-COPAUS1C-H2) (COPAUS1C-032), so the observations of COPAUS2C-001, COPAUS2C-007 to COPAUS2C-009 and the joint commit of COPAUS2C-012 that exist only after it assert nothing; a failed `ASKTIME` or `FORMATTIME` is X-COPAUS2C-H3, and the hour-24 and day-00 timestamp texts are X-COPAUS2C-H4.
- Behaviour constraint and R7 — Anomaly handling: audited defects are expected results (the key collision of X-COPAUS2C-1 is reproduced); anomalies are proposed after the table, never smoothed over.
- R16 — Authority and protected paths: `app/**` is read only; this file is the only output.

## Escalation candidates

- `X-COPAUS2C-1`
  - Found in: `app/app-authorization-ims-db2-mq/cbl/COPAUS2C.cbl:103-111,171-172`; `app/app-authorization-ims-db2-mq/cbl/COPAUA0C.cbl:871-877`; `app/app-authorization-ims-db2-mq/ddl/AUTHFRDS.ddl:28`; `app/app-authorization-ims-db2-mq/ims/DBPAUTP0.dbd:36-37`.
  - Anomaly class: declaration-not-followed.
  - Finding: `AUTH_TS` joins the requester's authorization date (`PA-AUTH-ORIG-DATE`, request token 1 as received) with CP00's processing time of day from the inverted key, and drops the processing date that the IMS key holds in `PA-AUTH-DATE-9C`. The column therefore names no instant at which anything happened, and two different authorizations of one card with the same request date, processed on different days at the same hour, minute, second and millisecond, get the same `(card_num, auth_ts)`.
