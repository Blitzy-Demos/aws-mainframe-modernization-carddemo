# COUSR03C — user delete (CU03)

This is the derive-lane (#2) audit of `COUSR03C`, the CICS program behind transaction `CU03`, map `COUSR03` (`COUSR3A`) and route `/users/delete`. It is written before `modern/crates/domain/src/online/cousr03c.rs`, `modern/crates/api/src/services/cousr03c.rs`, `modern/crates/api/src/dto/cousr03c.rs`, `modern/crates/api/src/handlers/cousr03c.rs` and `modern/crates/api/tests/endpoints_users.rs`, and code that consumes it is accepted only once this file is `Accepted` in the status table of `../README.md` (a8, a9; AAP 0.8.6). The program is read in place at commit `59cc6c2` and never modified (R16).

The program is served by two admin endpoints (`[A]`, AAP 0.3.4.1):

- Endpoint 18, `GET /api/v1/users/{user_id}` → `UserView { user_id, first_name, last_name, user_type }`, the fetch (ENTER). It is shared with COUSR02C (CU02), because the two programs' read paragraphs carry identical not-found and lookup literals (AAP 0.2.3), and its DTO, handler and service live in the `cousr02c` modules. Its rules are rows of `online/COUSR02C.md`: the read rows are `COUSR02C-nnn`. This file holds one reference row for each read literal, naming the COUSR02C row it equals, and the rows for what the `COUSR03` screen does with the response.
- Endpoint 20, `DELETE /api/v1/users/{user_id}` → `ScreenResult`. It serves PF5 (`F5=Delete`), and its DTO, handler and service live in the `cousr03c` modules.
- Errors of both are `ScreenError { message, field? }`.

## Reading the table

- Rule ID: `COUSR03C-<nnn>`, in this order: access and entry, keys, the fetch, the delete, then screen-wide behaviour.
- Program: `COUSR03C`; the reference rows add `COUSR02C`.
- Paragraph: the COBOL paragraph, with the AID or `RESP` branch where it decides the row.
- Copybook field or PIC: the map field (`COUSR03.CPY`), record field (`CSUSR01Y`) or working-storage item the rule tests or moves.
- Input condition: the request or the screen event. Map and DTO fields correspond as `USRIDIN` ↔ the path `user_id`, `FNAME` ↔ `first_name`, `LNAME` ↔ `last_name` and `USRTYPE` ↔ `user_type`. The map has no password field.
- Expected result: for a `server` row, the status, the message exactly as the program moves it (trailing dots kept), the `ScreenError` `field`, the response values and the effect on `users`. The `field` is the input on which the COBOL places the cursor (`MOVE -1 TO <field>L`). For a `client` row, what the screen does.
- Reference rows (COUSR03C-010, COUSR03C-013 and COUSR03C-014): the Expected result reads `same as COUSR02C-nnn (shared endpoint 18)` and repeats the cited row's literal only for the reader. A reference row adds no independently tested rule: the cited row governs, and a revision of it revises the reference row.
- Blank and padding: as in `online/COUSR02C.md`. A blank value is empty, all spaces or all NUL after padding, which is what `= SPACES OR LOW-VALUES` tests; any other character, leading spaces included, makes it non-blank. Request strings are padded on the right with spaces to the field's PIC width before any edit or comparison. COUSR03C upper-cases nothing. `USRIDIN`, `FNAME`, `LNAME` and `USRTYPE` are `FSET`, so ENTER and F5 always transmit the user ID as typed and the values shown.
- Where one task sends the map more than once (the read's prompt, then the final message), the terminal shows the last send, and the row states that one. On F5, `DELETE-USER-INFO` sends after the read and again after the delete, and endpoint 20 returns only the final result.
- Message colour: `DFHNEUTR` and `DFHGREEN` render as the `MessageLine` `default` variant, the map's `RED` (COUSR03-025) as `destructive`. A send whose path sets no colour shows the map's red.

## Rules governing this file

- Cardholder Data Redaction: COUSR03C never moves `SEC-USR-PWD` to its map, which has no password field, and no response, `ScreenError`, log line or span of endpoints 18 and 20 carries a password (CSUSR01Y-004). User IDs, names and types are not protected values (AAP 0.3.4.8).
- Identity and Trust (AAP 0.5.1): the path `user_id` names the target user and is validated input like any other field. The caller acts only as the verified token's `sub` and `usr_type`, which neither select nor restrict the target: COUSR03C never compares the target with `CDEMO-USER-ID`, so an admin may delete any user, themselves included (COUSR03C-024).
- Behaviour constraint: the replacement keeps COUSR03C's edits, their order, its messages and its store effects, defects included: the delete failure says `Update` (X-COUSR03C-1), and F5 deletes the user ID in the input without a prior fetch or any confirmation beyond the key itself (COUSR03C-017, COUSR03C-023). Under R7 — Anomaly handling, anomalies are proposed below as candidates, never smoothed over.
- Messages and HTTP status: 400 input error, 401 missing or invalid token, 403 admin gate, 404 not found, 500 store failure. Neither endpoint is a collection, so Bounded Pagination does not apply, and no 409 exists, because COUSR03C has no changed-by-another-user check.
- Thin Request Handlers and R16: every branch of these rows belongs to `domain::online::cousr03c` and `api::services::cousr03c` (and, for endpoint 18, their `cousr02c` counterparts), never to a handler; this file is markdown under `modern/audit/`, and `app/**` is read only.
