# COPAUS1C — authorization detail (CPVD, endpoints 22 and 23)

This is the derive-lane (#2) audit of COPAUS1C, `app/app-authorization-ims-db2-mq/cbl/COPAUS1C.cbl` (604 lines), "Detail View of Authorization Message", the CICS program of transaction `CPVD`, which sends and receives map `COPAU1A` of mapset `COPAU01`. It shows one pending authorization of the account COPAUS0C listed, steps to the next one, and marks or unmarks it as fraud through COPAUS2C. Its replacement is endpoint 22, `GET /api/v1/authorizations/{acct_id}/{auth_key}` with the query parameter `direction` (absent for ENTER, `next` for F8), returning `AuthDetailResponse`; endpoint 23, `POST /api/v1/authorizations/{acct_id}/{auth_key}/fraud`, returning `FraudToggleResult`; and the screen `frontend/src/screens/COPAU01.tsx` at route `/authorizations/detail` (AAP 0.3.4.1, 0.3.5).

- `acct_id` is the 11-digit account the COMMAREA carries (`CDEMO-ACCT-ID PIC 9(11)`, COCOM01Y-012). `auth_key` names one detail by its 8-byte `PA-AUTHORIZATION-KEY`, the IMS sequence field `PAUT9CTS`: the inverted date `PA-AUTH-DATE-9C PIC S9(05) COMP-3` followed by the inverted time `PA-AUTH-TIME-9C PIC S9(09) COMP-3` (CIPAUDTY-001, CIPAUDTY-002). The API carries it as the pair (`auth_date_9c`, `auth_time_9c`) that endpoint 21 returns for each list row (COPAUS0C-034); the text form of the path segment is fixed by the DTO, not by the COBOL, and is the same in endpoints 21, 22 and 23.
- The IMS database `DBPAUTP0` is the root segment `PAUTSUM0` → table `pending_auth_summaries` (primary key `acct_id`) and the child segment `PAUTDTL1` → table `pending_auth_details` (primary key `acct_id`, `auth_date_9c`, `auth_time_9c`), migration `0004_authorizations.sql`. COPAUS2C's Db2 table `AUTHFRDS` → `auth_fraud`, in the same migration.
- The store half of F5, the `auth_fraud` row and the status and message COPAUS2C hands back, is audited in `online/COPAUS2C.md`; the F5 rows here cite its IDs and hold the key handling, the detail replace, the commit or rollback and the messages.
- This file comes before `crates/domain/src/online/copaus1c.rs`, `crates/api/src/services/copaus1c.rs`, `crates/api/src/{dto,handlers}/copaus1c.rs`, `crates/api/tests/endpoints_authorizations.rs` and the COPAU01 screen. Code that consumes it is accepted only once the reviewer marks it `Accepted` in the status table of `../README.md` (a8, a9; AAP 0.8.6). Paths under `crates/` and `frontend/` are relative to `modern/`. Every source was read in place at commit `59cc6c2` and none was changed (R16).

## Reading the table

- Rule ID: `COPAUS1C-<nnn>`, in this order: entry and keys (001–005), the read and its messages (006–011), the detail display (012–023), F8 (024–027), F5 (028–034), then the rows that hold for every send and the halted code fields (035–038).
- Paragraph: the COPAUS1C paragraph that holds the rule; `→` names a paragraph it performs.
- Copybook field or PIC: the fields the rule reads or writes, with their PICs and, for a copybook field, its `../copybooks.md` row; map fields are named by their symbolic-map field.
- Input condition: the key, the request or the data state. "The state" is what the screen keeps between interactions, as the COBOL keeps it in the COMMAREA: `acct_id` (`CDEMO-ACCT-ID`) and `auth_key` (`CDEMO-CPVD-PAU-SELECTED`).
- Expected result: what the screen shows or the endpoint returns. A message row gives the literal as the program moves it, in COBOL quotes so that leading spaces show, and the status the endpoint returns with it: 400 input error, 404 not found, 500 store failure; every other response is 200. The message row of the map holds 78 characters (`ERRMSG LENGTH=78`). Display values travel in `AuthDetailResponse` and `FraudToggleResult` as the strings given here, built with the program's pictures; the screen formats nothing. An error response is a `ScreenError` and carries no detail field.
- Layer: as `../README.md` defines it; `client` rows include what the screen renders and the state it keeps.

## Rules governing this file

- Cardholder Data Redaction (E32): the COBOL shows the full card number on this screen; endpoints 22 and 23 return only the redacted form (COPAUS1C-012). This file quotes no fixture card number or account value; the worked values are invented.
- Typed Dates and Timestamps: the rule covers the five `PIC X(10)` dates and the `PIC X(26)` timestamps. The dates and times this screen shows come from `PA-AUTH-ORIG-DATE` and `PA-AUTH-ORIG-TIME` (`X(06)`), `PA-CARD-EXPIRY-DATE` (`X(04)`) and `PA-FRAUD-RPT-DATE` (`X(08)`), which `../copybooks.md` keeps as text (CIPAUDTY-003, CIPAUDTY-004, CIPAUDTY-007, CIPAUDTY-027), so they travel as the display strings COPAUS1C-013, COPAUS1C-014, COPAUS1C-020 and COPAUS1C-022 derive, as on COPAU00 (COPAUS0C-034); `../screens.md` row COPAU01-015, which X-COPAUS1C-5 found calling Auth Date a typed date, now treats it as the display string of COPAUS1C-013.
- Equivalence failure constraint, H3 and H4: every IMS status strung into a message is COPAUS1C-038, `HALTED(H4)`, and asserts nothing (X-COPAUS1C-H4); the Db2 codes in the message COPAUS2C hands back are `HALTED(H3)` in COPAUS2C-010 and COPAUS2C-011 and cited here as halt H3 (COPAUS1C-031). A row whose case a halt candidate below names says `HALTED(X-COPAUS1C-Hn)` for that case and asserts nothing for it; the message rows cite halt H4 for the parts it leaves assertable.
- Behaviour constraint and R7 — Anomaly handling: the defects found are expected results and are reproduced, apart from the cases the candidates hand to the reviewer; anomalies are proposed below as `X-COPAUS1C-<n>` and never normalised.
- Thin Request Handlers: the flag toggle, the detail-not-found and read-failure outcomes, the commit or rollback and the message choice belong to `domain::online::copaus1c` and `api::services::copaus1c`; the handlers extract, call one service function and map its outcome.
- Bounded Pagination: endpoints 22 and 23 address one authorization each and are not collection endpoints; they take no `page_size`.
- R16 — Authority and protected paths: `app/**` is read only; this file is the only one written.
