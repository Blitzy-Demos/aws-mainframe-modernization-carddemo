# COUSR01C — user add (CU01)

This is the derive-lane (#2) audit of `COUSR01C` (299 lines), the CICS program of transaction `CU01` that adds a regular or admin user to the `USRSEC` file. The replacement serves it as endpoint 17, `POST /api/v1/users` [A], which takes a `UserAddRequest` and returns a `ScreenResult`, and as the screen `COUSR01` at route `/users/add`. The edits are `domain::online::cousr01c`; the password hashing and the insert are `api::services::cousr01c`, through `persistence::repos::users`; the handler only extracts, delegates and maps (Thin Request Handlers). Code that consumes this file is accepted only once the reviewer marks it `Accepted` in the status table of `README.md` (a8, a9; AAP 0.8.6). Every source was read in place at commit `59cc6c2` and none was changed (R16).

## Sources

- Program: `app/cbl/COUSR01C.cbl` (299 lines), reached only from the admin menu, option 2 `User Add (Security)` of `app/cpy/COADM02Y.cpy:31-34`.
- Record: `app/cpy/CSUSR01Y.cpy`, `SEC-USER-DATA`, 80 bytes (field rows CSUSR01Y-001 to CSUSR01Y-006 in `copybooks.md`, table `users`). COMMAREA: `app/cpy/COCOM01Y.cpy`, whose user ID and type the JWT claims replace.
- Screen: `app/bms/COUSR01.bms` and its symbolic map `app/cpy-bms/COUSR01.CPY`. The per-field rows are COUSR01-001 to COUSR01-038 in `screens.md` (labels, positions, `LENGTH`, the key-row labels and bindings, the header values); this file audits what the program does with them.
- Cross-references: `app/cpy/CSMSG01Y.cpy:20-21` (the invalid-key message) and `app/cbl/COSGN00C.cbl` (how sign-on reads what this program stores).

Source lines use short names: `COUSR01C.cbl` and `COSGN00C.cbl` are in `app/cbl/`; `CSUSR01Y.cpy`, `COCOM01Y.cpy`, `CSMSG01Y.cpy` and `COADM02Y.cpy` are in `app/cpy/`; `COUSR01.bms` is in `app/bms/`; `COUSR01.CPY` is in `app/cpy-bms/`.

## Reading the table

- Endpoint 17, `POST /api/v1/users`, admin gate `AdminUser`. ENTER is the only AID it serves, so `UserAddRequest` carries no `aid`. Its fields are `first_name` (`FNAME`, 20), `last_name` (`LNAME`, 20), `user_id` (`USERID`, 8), `password` (`PASSWD`, 8) and `user_type` (`USRTYPE`, 1). The server pads each value with spaces to its map length and reads an absent field as empty, so an empty field reaches COUSR01C's own message, never a deserialisation error.
- A `ScreenError`'s `field` names the field on which the COBOL puts the cursor (`MOVE -1 TO <field>L`).
- Success is HTTP 200 with a `ScreenResult` that holds the message only.
- Statuses: 400 for every input error, the duplicate user ID included, because `README.md` reserves 409 for a record changed by another user and the duplicate is input the operator must change (field `user_id`); 401 for a missing, invalid or expired token; 403 for the admin gate; 500 for a store failure. 404, 409 and every other status are unused; endpoint 17 is not a collection endpoint, so the page-size rejection of Bounded Pagination does not apply to it.
- PF3, PF4, F12 and every other key send no request (AAP 0.3.4.1), so their rows are `client`.
- Rule ID: `COUSR01C-<nnn>`, from 001, in the order gate, `MAIN-PARA`, `PROCESS-ENTER-KEY`, record build, `WRITE-USER-SEC-FILE`, then the screen behaviour around them.
- Program: `COUSR01C`. Paragraph: the paragraph whose statements the row audits; several are separated by `;`.
- Copybook field or PIC: the symbolic-map field (`COUSR01.CPY`), the record field (`CSUSR01Y`) or the COMMAREA field (`COCOM01Y`) the rule reads or writes.
- Input condition: the request or key and the state that select the rule. "Empty" means the field, padded with spaces to its map length, is all spaces: the request value is absent, empty or only spaces. COBOL's `SPACES OR LOW-VALUES` test also catches a field the operator erased, which the terminal sent as nulls; in a request that case is an absent or empty value.
- Expected result: the HTTP status, the `ScreenError` or `ScreenResult` message exactly as the program moves it (quoted without the trailing spaces of `WS-MESSAGE PIC X(80)`), the `field`, the effect on `users`, or, for a `client` row, what the screen shows.

## Rules governing this file

- Cardholder Data Redaction: this file quotes no password value. The password is stored only as its argon2id hash (E25) and appears in no response, log, span or error (COUSR01C-018).
- Identity and Trust (AAP 0.5.1): the acting identity is the verified token's. The body's `user_id` and `user_type` describe the user being added and grant the caller nothing (COUSR01C-026).
- Behaviour constraint and R7 — Anomaly handling: E26 is preserved (COUSR01C-019), defects are reproduced, and the anomalies found are proposed below as `X-COUSR01C-<n>` and `X-COUSR01C-H1`, never normalised.
- Client schema: the `COUSR01` zod schema (`frontend/src/schemas/COUSR01.ts`) enforces each field's map `LENGTH` (the `both` rows of `screens.md`) and repeats none of COUSR01C's edits. The COBOL shows exactly one message, the first failing check in `EVALUATE` order, and the server owns every message (AAP 0.3.5). Every `PROCESS-ENTER-KEY` row is therefore `server`, and the schema must not restrict `user_type` to `A` and `U` (COUSR01C-015).
- Thin Request Handlers: the empty-field edits are domain rules, the hash (`domain::password::hash`) and the insert run in the service, and the handler maps the outcome with the `dto` and `error` conversions.

## Escalation candidates

Proposed under R7 — Anomaly handling. The reviewer folds each candidate into `ESCALATIONS.md` under the next free ID, as its `## Later entries` section describes; until then the rows above cite the candidate name.

- `X-COUSR01C-1`
  - Found in: `app/cbl/COUSR01C.cbl:154`; `app/cbl/COSGN00C.cbl:132-134,209-216`.
  - Anomaly class: declaration-not-followed.
  - Finding: the user ID is stored as typed, but sign-on upper-cases the entered ID before it reads `USRSEC`, so a user added with a lower-case letter in its ID can never sign on. E26 records the same pattern for the password only.
  - Proposed resolution: preserved (Behaviour constraint): endpoint 17 stores the ID as typed and endpoint 1 upper-cases it before the read (COUSR01C-020). The reviewer may fold the case into E26. The same case is proposed from the sign-on side as `X-COSGN00C-1` in `online/COSGN00C.md`; the two are folded into one escalation.
- `X-COUSR01C-2`
  - Found in: `app/bms/COUSR01.bms:146-150`; `app/cbl/COUSR01C.cbl:142-147,158`; `app/cpy/COCOM01Y.cpy:27-28`; `app/cbl/COSGN00C.cbl:230`.
  - Anomaly class: declaration-not-followed.
  - Finding: the screen prompts `(A=Admin, U=User)` and the COMMAREA defines only `A` and `U`, but COUSR01C rejects only an empty type, so any other character, lower-case `a` included, is stored; sign-on treats every value but `A` as a regular user.
  - Proposed resolution: preserved: any non-empty type is accepted and stored as typed, the zod schema does not narrow it, and only `A` passes `AdminUser` and routes to `/admin` (COUSR01C-015). The `usr_type` column has no value-list `CHECK` (migration 0003, CSUSR01Y-005).
- `X-COUSR01C-3`
  - Found in: `app/cbl/COUSR01C.cbl:153-158`; `modern/audit/copybooks.md` (PIC-001, PIC-002).
  - Anomaly class: request-vs-repository.
  - Finding: a request field can carry a character outside printable ASCII (0x20–0x7E), such as an accented letter or a control character. The terminal sent the characters of its code page and COUSR01C stores whatever arrives, but `PicX<N>` holds printable ASCII only and returns a typed error for anything else (PIC-002), and no COUSR01C message covers the case. The same holds for every text input of the online endpoints.
  - Proposed resolution: endpoint 17 rejects such a value with HTTP 400 and a `ScreenError` naming the field, before COUSR01C's edits run, as it rejects a value longer than the map `LENGTH` (COUSR01-013, COUSR01-016, COUSR01-019, COUSR01-022, COUSR01-025). The message is the request validation's, not a COBOL literal, and no parity is claimed for it; the reviewer settles the text once for all online endpoints.

## Halt candidates

Cases found while deriving the rows above that have no single result. Each is proposed to join an existing halt, and the reviewer folds it into `HALTS.md` under its `## Later entries` procedure. Until then, no parity assertion is written for the value it names.

- `X-COUSR01C-H1`, proposed to join H2.
  - Path: `app/cbl/COUSR01C.cbl:53,153-160,240-248`; `app/cpy/CSUSR01Y.cpy:17-23`. `SEC-USER-DATA` is copied into WORKING-STORAGE with no `VALUE`.   - Why no single result: the 23 bytes written are the record's initial storage, which depends on runtime storage initialisation that nothing in the repository sets, as in H2.
  - Bindings blocked: g1b: the `users.filler` value of the row COUSR01C-016 inserts (COUSR01C-017). Every other column stays assertable, and endpoint 17 returns no filler.
  - Escalation: none yet; the reviewer adds one to `ESCALATIONS.md` when folding the candidate in.
  - Candidate resolution: as H2.
