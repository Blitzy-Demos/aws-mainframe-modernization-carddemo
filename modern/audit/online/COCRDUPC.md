# COCRDUPC audit — card update (CCUP)

This is the derive-lane (#2) audit of `COCRDUPC` (1,560 lines), the program behind transaction `CCUP`, map `COCRDUP` (`CCRDUPA`) and route `/cards/update`. Its rows are the expected results for `modern/crates/domain/src/online/cocrdupc.rs`, `modern/crates/api/src/services/cocrdupc.rs` and `modern/crates/api/src/{dto,handlers}/cocrdupc.rs`, proved by `modern/crates/api/tests/endpoints_cards.rs` and the frontend tests named below. Code that consumes this file is accepted only once the reviewer marks it `Accepted` in the status table of `modern/audit/README.md` (a8, a9). The COBOL was read in place at commit `59cc6c2` and not changed (R16).

## Sources

- Program: `app/cbl/COCRDUPC.cbl`. Copybooks: `app/cpy/CVACT02Y.cpy` (card record), `app/cpy/COCOM01Y.cpy` (COMMAREA), `app/cpy/CVCRD01Y.cpy` (`CC-ACCT-ID`, `CC-CARD-NUM`, the AID flags) and `app/cpy/CSSTRPFY.cpy` (AID mapping, copied at `COCRDUPC.cbl:1528`).
- Map: `app/bms/COCRDUP.bms` and its symbolic map `app/cpy-bms/COCRDUP.CPY`; the map rows themselves are `COCRDUP-001` to `COCRDUP-044` of `modern/audit/screens.md`.
- Callers: `app/cbl/COCRDLIC.cbl:545-569` (a `U` selection) and `app/cbl/COMEN01C.cbl:177-187` (menu option); both transfer with the 160-byte `CARDDEMO-COMMAREA` only.
- Fixture: `app/data/ASCII/carddata.txt`, cited as `carddata.txt:<line>`.
- Vendor semantics, IBM documentation: `FUNCTION TRIM` of an all-space argument returns a value of length zero (Enterprise COBOL for z/OS 6.4 Language Reference, "TRIM"); `INITIALIZE` without the `FILLER` phrase ignores elementary FILLER items (same reference); a numeric item that holds non-numeric data gives unpredictable results when referenced (Enterprise COBOL 6.4 Programming Guide); `JUSTIFY=(RIGHT)` without `BLANK` or `ZERO` fills with zeros (CICS TS DFHMDF macro reference).

Source lines use short names: `COCRDUPC.cbl`, `COCRDLIC.cbl` and `COMEN01C.cbl` are in `app/cbl/`, `.cpy` in `app/cpy/`, `COCRDUP.bms` in `app/bms/`, `COCRDUP.CPY` in `app/cpy-bms/` and `carddata.txt` in `app/data/ASCII/`.

## Endpoints, states and messages

- Endpoint 9, `GET /api/v1/cards/edit`, `CardLookupQuery { acct_id, card_num? | card_ref? }` → `CardUpdateView`: the redacted card number, `card_ref`, the account as entered, the fetched name, expiry date and status, and the snapshot. It serves ENTER while no details are shown (the search) and the entry from the card list.
- Endpoint 10, `PUT /api/v1/cards/{card_ref}`, `CardUpdateRequest { aid, fields, snapshot }` → `CardUpdateResult`. `aid` ENTER runs the change check and the edits and asks for confirmation; `aid` PF5 saves.
- F3 and F12 send no request (AAP 0.3.4.1); F5 saves in state `N`, and every other key is ENTER (COCRDUPC-007, COCRDUPC-008).
- State: `CCUP-CHANGE-ACTION` (`COCRDUPC.cbl:276-290`), which the rows name by its code: not fetched (spaces or low-values), `S` details shown, `E` changes not OK, `N` changes validated and not confirmed, `C` changes saved, `L` lock failed, `F` rewrite failed. The COBOL keeps it and `CCUP-OLD-DETAILS` in the COMMAREA between tasks; the replacement returns both in the snapshot, which the client echoes and which grants nothing (COCRDUPC-044, X-COCRDUPC-1).
- Info message: `3250-SETUP-INFOMSG` (`COCRDUPC.cbl:1138-1164`) derives the info line from the state alone: not fetched `Please enter Account and Card Number`, `S` `Details of selected card shown above`, `E` `Update card details presented above.`, `N` `Changes validated.Press F5 to save`, `C` `Changes committed to database`, `L` and `F` `Changes unsuccessful. Please try again`.
- Error message: `WS-RETURN-MSG PIC X(75)`; each edit sets it only while it is still blank, so the first failing check wins.

## Reading the table

- Rule ID `COCRDUPC-<nnn>`, numbered in the order of the flow: entry and keys, receive, search, fetch, change check, edits, confirmation, save, then the rows the replacement adds and the screen-only rows.
- Paragraph: the COBOL paragraph whose statements the row audits. Copybook field or PIC: the fields the rule reads or writes, as declared.
- Input condition: the endpoint, the `aid`, the state the request echoes and the field values; or, for a `client` row, the key or event.
- Expected result: the HTTP status, the error message and the field it names, the info message, the state after the response, what the screen shows and what is written. A 200 response returns the state in its snapshot. An error response is a `ScreenError` (message and field only), so the screen sets the state the row names, which the message determines, keeps the last snapshot unless the row says otherwise, and shows that state's info message. Statuses follow `modern/audit/README.md`: 400 input error, 404 not found, 409 changed by another user, 500 store failure; this program serves no collection endpoint, so the page-size rejection of Bounded Pagination never occurs.
- Message literals appear in backticks exactly as the program moves them, without the trailing spaces of their receiving field.
- A field value written `blank` means spaces, low-values (an erased field) or the single character `*` followed by spaces, which `1100-RECEIVE-MAP` treats alike (COCRDUPC-009).

- `server` rows: `modern/crates/api/tests/endpoints_cards.rs`, over the fixture-loaded database, each test tagged `// audit: COCRDUPC-<nnn>`. Store failures (COCRDUPC-019, -036, -040) are injected through a repository test double.

- No row is `both`. The map declares no `NUM` attribute, its `LENGTH` limits are the `both` rows of `screens.md` (COCRDUP-013, -016, -019, -022, -025, -027), and no COCRDUP zod schema repeats a program edit, because each edit's message, state change and info line come from the server.
- A row that cites a halt candidate asserts nothing for the case the candidate names; its test reports that case `BLOCKED`.

## Rules governing this file

- Cardholder Data Redaction (E32): this file quotes no card number, CVV or SSN. Responses show the card number as twelve `*` followed by its last four digits and identify the card by `card_ref`; no request carries the full number after the search, and no response carries the CVV (COCRDUPC-042 to COCRDUPC-044, X-COCRDUPC-4).
- Typed Dates and Timestamps: the stored expiry date is a typed date (`CVACT02Y-005`), returned typed by endpoint 9. The month and year are raw screen parts that `1250-EDIT-EXPIRY-MON` and `1260-EDIT-EXPIRY-YEAR` edit, the exception AAP 0.3.4.1 makes; the day comes from the snapshot's date (COCRDUPC-038, X-COCRDUPC-3).
- Equivalence failure constraint: COCRDUPC-019 is `HALTED(H4)`. The halt candidates below block the cases they name until the reviewer folds them in or rejects them.
- Behaviour constraint and R7 — Anomaly handling: audited defects are expected results (the account rewritten from the search key, the upper-cased name written back, the case-blind change check, the card whose stored name fails the alphabet edit); anomalies are proposed as candidates, never smoothed over.
- Thin Request Handlers: the state machine of `2000-DECIDE-ACTION` and every branch below live in `domain::online::cocrdupc` and `api::services::cocrdupc`; the handlers only extract, delegate and map.
- R16 — Authority and protected paths: `app/**` is read only.

## Escalation candidates

Proposed under R7 — Anomaly handling. The reviewer folds each candidate into `ESCALATIONS.md` under the next free ID, as its `## Later entries` section describes; until then the rows above cite the candidate names.

- `X-COCRDUPC-1`
  - Found in: `app/cbl/COCRDUPC.cbl:274-313,413-424,546-558,685-692,1191-1199`.
  - Anomaly class: request-vs-repository.
  - Finding: the program is pseudo-conversational: `CCUP-CHANGE-ACTION` and `CCUP-OLD-DETAILS` survive between tasks in the COMMAREA, and they decide whether PF5 saves (state `N` only), which info line accompanies a no-change answer (`S` or `E`) and what the change check compares. Endpoint 10 is stateless. In state `N` every field is protected, so the COBOL skips the edits on a PF5 because it receives back exactly the values it validated; a REST client can send other values.
  - Proposed resolution: the snapshot carries the fetched values (without the card number and the CVV) and the state after each response, and the client echoes it unchanged (COCRDUPC-044). It grants nothing: a PF5 with state `N` re-runs the change check and the edits on the received fields before saving, which gives the COBOL's result for every input a 3270 can send (COCRDUPC-041). An error response is a `ScreenError`, so the screen sets the state the row names from its message; after a 409 it takes the card's current values from endpoint 9 (COCRDUPC-037). States `C`, `L` and `F` are never echoed, because the next key is client navigation (COCRDUPC-005).
- `X-COCRDUPC-2`
  - Found in: `app/cbl/COCRDUPC.cbl:201-202,1376-1390,1424-1425,1463`.
  - Anomaly class: declaration-not-followed.
  - Finding: `9100-GETCARD-BYACCTCARD` reads the card by its number alone (the account key is commented out at lines 1379 and 1424, and `DID-NOT-FIND-ACCT-IN-CARDXREF` is never set), so a card of another account is found under the account entered, and `9200-WRITE-PROCESSING` rewrites `CARD-ACCT-ID` from that entered account (`CC-ACCT-ID-N`), moving the card to it.
  - Proposed resolution: preserved (Behaviour constraint): endpoint 9 does not check the pair, and the save writes the account the snapshot carries (COCRDUPC-016, COCRDUPC-038).
- `X-COCRDUPC-3`
  - Found in: `app/cbl/COCRDUPC.cbl:1365-1366,1467-1474`; `app/data/ASCII/carddata.txt:35`.
  - Anomaly class: refinement-override.
  - Finding: the rewritten expiry date is the text year `-` month `-` stored day, with no date check. A month the edits accept can make it no calendar date: the card of `carddata.txt:35` expires on day 29, so month `02` with year `2025` composes `2025-02-29`; a stored date that is blank leaves the day as two spaces. The COBOL writes such text into `CARD-EXPIRAION-DATE`; under Typed Dates and Timestamps the column is `DATE` (`CVACT02Y-005`, `PIC-016`) and cannot hold it.
  - Proposed resolution: endpoint 10 validates and confirms as the COBOL does; at the save, a date that is no calendar date ends as the rewrite failure of COCRDUPC-040 (500 `Update of record failed`, state `F`, nothing written). That outcome is not claimed as parity.
- `X-COCRDUPC-4`
  - Found in: `app/cbl/COCRDUPC.cbl:1354,1503,1512`.
  - Anomaly class: refinement-override.
  - Finding: `9300-CHECK-CHANGE-IN-REC` compares the CVV read for update with the CVV kept from the fetch. Under Cardholder Data Redaction no DTO carries a CVV (`CVACT02Y-003`), so the stateless save has no fetched CVV to compare.
  - Proposed resolution: the comparison drops the CVV term and keeps the name, expiry date and status terms (COCRDUPC-037). A change that touched only the CVV between fetch and save is not detected; no online program but this one writes the CVV.
