# COTRN01C — transaction view (CT01, endpoint 12)

This is the derive-lane (#2) audit of `COTRN01C`, the 330-line CICS program behind transaction `CT01` and map `COTRN01` (`COTRN1A`, route `/transactions/view`). It views one record of the `TRANSACT` file by its key. The replacement serves the program's one read paragraph as endpoint 12, `GET /api/v1/transactions/{tran_id}` → `TranViewResponse` (AAP 0.3.4.1), for any signed-on user. The rows below come before `crates/domain/src/online/cotrn01c.rs`, `crates/api/src/services/cotrn01c.rs`, `crates/api/src/{dto,handlers}/cotrn01c.rs` and the endpoint-12 cases of `crates/api/tests/endpoints_transactions.rs`, and code that consumes them is accepted only once this file is `Accepted` in the status table of `modern/audit/README.md` (a8, a9). The COBOL was read in place at commit `59cc6c2` and not changed (R16).

- Map: `app/bms/COTRN01.bms` and its symbolic map `app/cpy-bms/COTRN01.CPY`; field positions, attributes, header values and key labels are rows `COTRN01-001` to `COTRN01-066` of `modern/audit/screens.md`, which this file does not repeat.
- File definition: `app/csd/CARDDEMO.CSD` (`TRANSACT`), read only for the update-intent read (X-COTRN01C-2), a source outside the inventory like those of E22.
- Field types and columns: `CVTRA05Y-001` to `CVTRA05Y-014`, `PIC-017` to `PIC-021` (timestamp layouts) and `PIC-024` (sensitive fields) of `modern/audit/copybooks.md`.

Source lines use short names: `.cbl` files are in `app/cbl/`, `.cpy` files in `app/cpy/`, `COTRN01.bms` in `app/bms/`, `COTRN01.CPY` in `app/cpy-bms/` and `CARDDEMO.CSD` in `app/csd/`.

## Reading the table

- Rule ID: `COTRN01C-<nnn>`, in paragraph order: `MAIN-PARA`, `PROCESS-ENTER-KEY`, `READ-TRANSACT-FILE`, the field moves of a successful read, then the send paragraphs.
- Input condition: the screen state or AID as the program sees it, and, for a `server` row, the request that reproduces it. `tran_id` is the path parameter of endpoint 12, which carries the Tran ID input `TRNIDIN`.
- Expected result: messages are quoted exactly as the program moves them, with the HTTP status of endpoint 12 and the `ScreenError` field; every error places the cursor on `TRNIDIN` (`MOVE -1 TO TRNIDINL`), so the field is `tran_id`.
- Field rows (`COTRN01C-016` to `COTRN01C-028`) name the map field the COBOL moves a record field into. `TranViewResponse` carries one value per such field, the bytes the screen shows: text fields as their `PicX` bytes, trailing spaces included and cut to the map width where the map field is narrower; numeric codes and IDs as their digits with leading zeros; the amount as the edited string; the two timestamps as typed values. The screen renders them unchanged and formats nothing but the typed timestamps (AAP 0.3.4.1).
- Layer: `server` for what endpoint 12 returns or stores, `client` for what the screen does without a request, `both` for the one check the screen's zod schema repeats (`modern/audit/README.md`, "Layers and required tags").

## How the rows are proved

- `server` rows: `crates/api/tests/endpoints_transactions.rs`, against a migrated, fixture-loaded database with transactions posted by `posttran` or inserted by the test, with a `U` and an `A` token.
- `client` rows: `frontend/src/screens/COTRN01.test.tsx` (rendering, PF4, the invalid-key message, the pre-filled fetch) and `frontend/e2e/nav.spec.ts` (sign-on redirect, PF3, PF5, the COTRN00 → COTRN01 selection).
- The `both` row: the server half in `endpoints_transactions.rs`, the client half in `frontend/src/schemas/COTRN01.test.ts`.
- Each proving test carries `// audit: <Rule ID>`.

## Rules governing this file

- Cardholder Data Redaction: `TRAN-CARD-NUM` reaches endpoint 12 only in its redacted form, twelve `*` followed by its last four characters, for every user type (`COTRN01C-017`, E32). This file quotes no card number.
- Typed Dates and Timestamps: `TRAN-ORIG-TS` and `TRAN-PROC-TS` travel as typed timestamps (OpenAPI `date-time`), `null` when blank. Their layout code (`I`, `D`, `S`) is a storage detail of `copybooks.md` and is not returned; the screen shows the date part the COBOL moves (`COTRN01C-023`, `COTRN01C-024`).
- Thin Request Handlers: every outcome below is decided in `domain::online::cotrn01c` and `api::services::cotrn01c`; the handler only extracts `tran_id` and the signed-on user, calls the service and maps the outcome.
- Behaviour constraint and R7 — Anomaly handling: audited defects are expected results; the anomalies found are proposed after the table as `X-COTRN01C-<n>`, and the case with no single result as `X-COTRN01C-H1`.
- Messages and HTTP status: endpoint 12 returns 400, 404 and 500 with the program's messages, and 200 on success.

## Escalation candidates

- `X-COTRN01C-1`
  - Found in: `app/cbl/COTRN01C.cbl:49,177,183`; `app/cpy/CVTRA05Y.cpy:10`.
  - Anomaly class: declaration-not-followed.
  - Finding: `WS-TRAN-AMT PIC +99999999.99` has eight integer digits against the nine of `TRAN-AMT PIC S9(09)V99`, so an amount of 100000000.00 or more loses its high-order digit on the screen. Such an amount can be stored, for example by a bill payment of a balance that large (`ARITH-021` of `modern/audit/arithmetic.md`).
  - Proposed resolution: preserved. Endpoint 12 returns the truncated string (`COTRN01C-022`); the stored amount is unchanged.
- `X-COTRN01C-2`
  - Found in: `app/cbl/COTRN01C.cbl:136-139,269-278`; `app/csd/CARDDEMO.CSD:76-84` (`UPDATE(YES)`, `RECOVERY(NONE)`).
  - Anomaly class: declaration-not-followed.
  - Finding: the view reads with `UPDATE`, which takes the record's update lock, but never rewrites, deletes or unlocks it; the lock lasts until the task ends at the `EXEC CICS RETURN` after the send. Its only effect is that a concurrent update of the same record would wait for that task to end.
  - Proposed resolution: not reproduced. Endpoint 12 reads without a lock and writes nothing (`COTRN01C-011`); no parity check observes the momentary lock.
- `X-COTRN01C-3`
  - Found in: `app/cbl/COTRN01C.cbl:103-109,152,191,288,295`.
  - Anomaly class: declaration-not-followed.
  - Finding: on a first entry with a selected ID, `PROCESS-ENTER-KEY` sends the map (line 152, 191, 288 or 295) and `MAIN-PARA` sends it again at line 109 with the same content and a freshly computed header time; the terminal shows the second send.
  - Proposed resolution: the screen renders the outcome once (`COTRN01C-003`). The final screen equals the COBOL's second send, header time compared by format; no binding asserts the first.

## Halt candidates

- `X-COTRN01C-H1`, proposing a new halt (H7 onward) whose candidate resolution it shares with H2.
  - Path: `app/cbl/COTRN01C.cbl:63,110-111,128-131,213-225,230-238`; `app/cpy-bms/COTRN01.CPY:17,145`. PA1, PA2, PA3 and CLEAR transmit no field data, so `RECEIVE MAP` raises `MAPFAIL`, which `RESP(WS-RESP-CD)` captures and nothing tests; `WHEN OTHER` then sends `COTRN1AO`, which redefines the `COTRN1AI` that no mapping filled in this task.
  - Why no single result: IBM documents that BMS does not set the input map to nulls on `MAPFAIL`, and `COTRN1AI` is working storage with no `VALUE`, allocated afresh for each pseudo-conversational task. What the Tran ID and detail fields show after those keys therefore depends on the storage-initialisation options of the deployed runtime and on how much of the unmapped input BMS moves, neither of which the repository sets. The message row (`Invalid key pressed. Please see below...`) and the header stay single-valued.
  - Bindings blocked: none that the replacement can reach. The browser has no PA or CLEAR key (`frontend/src/lib/pfkeys.ts` serves ENTER and F1 to F12), so `COTRN01C-007` covers F-keys only, and the PA and CLEAR variant gets no row and no assertion.
  - Escalation: none yet; the reviewer adds one to `ESCALATIONS.md` when folding the candidate in.
  - Candidate resolution: as H2, Language Environment storage-initialisation documentation for the deployed runtime options, with IBM's `RECEIVE MAP` `MAPFAIL` documentation; or user descoping, since the keys have no browser counterpart.
