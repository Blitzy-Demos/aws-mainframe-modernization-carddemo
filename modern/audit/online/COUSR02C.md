# COUSR02C — user update (CU02)

This is the derive-lane (#2) audit of `COUSR02C`, the CICS program behind transaction `CU02`, map `COUSR02` (`COUSR2A`) and route `/users/update`. It is written before `modern/crates/domain/src/online/cousr02c.rs`, `modern/crates/api/src/services/cousr02c.rs`, `modern/crates/api/src/dto/cousr02c.rs`, `modern/crates/api/src/handlers/cousr02c.rs` and `modern/crates/api/tests/endpoints_users.rs`, and code that consumes it is accepted only once this file is `Accepted` in the status table of `../README.md` (a8, a9; AAP 0.8.6). The program is read in place at commit `59cc6c2` and never modified (R16).

The program is served by two admin endpoints (`[A]`, AAP 0.3.4.1):

- Endpoint 18, `GET /api/v1/users/{user_id}` → `UserView { user_id, first_name, last_name, user_type }`, which never carries a password. It is shared with COUSR03C (CU03), because the two programs' read paragraphs carry identical not-found and lookup literals (AAP 0.2.3). Its DTO, handler and service live in the `cousr02c` modules (AAP 0.6.1). The rows marked "shared read (endpoint 18)" hold for both programs, and `online/COUSR03C.md` cites them instead of repeating them.
- Endpoint 19, `PUT /api/v1/users/{user_id}` with body `UserUpdateRequest { first_name, last_name, password?, user_type }` → `ScreenResult`. It serves PF5 (`F5=Save`) and the save half of PF3 (`F3=Save&Exit`, X-SCREENS-9).
- Errors of both are `ScreenError { message, field? }`.

## Reading the table

- Rule ID: `COUSR02C-<nnn>`, in this order: access and entry, keys, the shared read, the update, then screen-wide behaviour.
- Program: `COUSR02C`; the shared-read rows add `COUSR03C`, whose paragraphs are identical to these apart from the success prompt (X-COUSR02C-1).
- Paragraph: the COBOL paragraph, with the AID or `RESP` branch where it decides the row.
- Copybook field or PIC: the map field (`COUSR02.CPY`), record field (`CSUSR01Y`) or working-storage item the rule tests or moves.
- Input condition: the request or the screen event. Map and DTO fields correspond as `USRIDIN` ↔ the path `user_id`, `FNAME` ↔ `first_name`, `LNAME` ↔ `last_name`, `PASSWD` ↔ `password` and `USRTYPE` ↔ `user_type`.
- Expected result: for a `server` row, the status, the message exactly as the program moves it (trailing dots kept), the `ScreenError` `field`, the response values and the effect on `users`. The `field` is the input on which the COBOL places the cursor (`MOVE -1 TO <field>L`). For a `client` row, what the screen does.
- Blank: a value that is empty, all spaces or all NUL after padding, which is what `= SPACES OR LOW-VALUES` tests. A value holding any other character is not blank, leading spaces included.
- Padding: request strings are padded on the right with spaces to the field's PIC width before any edit or comparison, as BMS pads typed input to the field length. All five input fields are `FSET`, so ENTER, PF3 and PF5 always transmit them all. Response strings carry the stored value with trailing spaces removed (the trimmed view of `PicX`, AAP 0.3.3.1), which the map field displays identically. COUSR02C upper-cases nothing: it keys and stores what was typed.
- Where one task sends the map more than once (the read's prompt, then the final message), the terminal shows the last send, and the row states that one.
- Message colour: `DFHNEUTR` and `DFHGREEN` render as the `MessageLine` `default` variant, the map's `RED` and `DFHRED` as `destructive` (AAP 0.4.2, 0.4.3).

## Rules governing this file

- Cardholder Data Redaction: no password value appears here; password rows describe bytes, never a value. No response, `ScreenError`, log line or span of endpoints 18 and 19 carries a password (CSUSR01Y-004). User IDs, names and types are not protected values (AAP 0.3.4.8).
- Identity and Trust (AAP 0.5.1): the path `user_id` and the body name the target user and are validated input like any other field. The caller acts only as the verified token's `sub` and `usr_type`, which neither select nor restrict the target, so an admin may update any user, themselves included.
- Behaviour constraint and E27: the replacement keeps COUSR02C's edits, their order, its messages and its store effects. The one departure is the dark password field, which is never returned or pre-filled, so an omitted password means unchanged and a supplied one is compared through its hash (E27). Defects are reproduced; under R7 — Anomaly handling, anomalies are proposed below as candidates, never smoothed over.
- Messages and HTTP status: 400 input error, 401 missing or invalid token, 403 admin gate, 404 not found, 500 store failure. Neither endpoint is a collection, so Bounded Pagination does not apply, and no 409 exists, because COUSR02C has no changed-by-another-user check (COUSR02C-024).
- Thin Request Handlers and R16: every branch of these rows belongs to `domain::online::cousr02c` and `api::services::cousr02c`, never to the handler; this file is markdown under `modern/audit/`, and `app/**` is read only.
