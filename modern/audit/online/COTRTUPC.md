# COTRTUPC — transaction type maintenance (CTTU)

Derive-lane (#2) audit of `COTRTUPC`, the 1,702-line CICS and Db2 program behind transaction `CTTU`, map `CTRTUPA` of mapset `COTRTUP` (screen route `/transaction-types/maintain`). It fetches, adds, updates and deletes one row of the Db2 data version of the transaction types, `CARDDEMO.TRANSACTION_TYPE`, which the replacement holds as `db2.transaction_type` (migration `0006_db2_transaction_types.sql`). It never touches the VSAM data version (`transaction_types`), and nothing copies between the two versions (E23). The replacement serves it through endpoint 26, `GET /api/v1/transaction-types/{type_code}` → `TranTypeView`, and endpoint 27, `POST /api/v1/transaction-types/{type_code}/actions` with `TranTypeActionRequest { aid, description? }` → `TranTypeActionResult`, both admin-only (`[A]`). This file supplies `crates/domain/src/online/cotrtupc.rs`, `crates/api/src/{services,dto,handlers}/cotrtupc.rs`, `crates/api/tests/endpoints_transaction_types.rs`, the COTRTUP screen, its zod schema and their tests. Code that consumes it is accepted only once the reviewer marks it `Accepted` in `modern/audit/README.md` (a9).

## Reading the table

### Program states

COTRTUPC is pseudo-conversational. Between screens its COMMAREA keeps `TTUP-CHANGE-ACTION PIC X(1)` (lines 296-327), the fetched values `TTUP-OLD-TTYP-TYPE`/`-DESC` and the entered values `TTUP-NEW-TTYP-TYPE`/`-DESC`. Rows name the states by their values:

- fresh: `TTUP-DETAILS-NOT-FETCHED` (low-values or spaces), the screen with no type fetched;
- X `TTUP-DETAILS-NOT-FOUND`, S `TTUP-SHOW-DETAILS`, R `TTUP-CREATE-NEW-RECORD`;
- E `TTUP-CHANGES-NOT-OK`, N `TTUP-CHANGES-OK-NOT-CONFIRMED`, B `TTUP-CHANGES-BACKED-OUT`;
- C `TTUP-CHANGES-OKAYED-AND-DONE`, L `TTUP-CHANGES-OKAYED-LOCK-ERROR`;
- 9 `TTUP-CONFIRM-DELETE`, 8 `TTUP-START-DELETE`, 7 `TTUP-DELETE-DONE`, 6 `TTUP-DELETE-FAILED`.

`TTUP-INVALID-SEARCH-KEYS` ('K') is overwritten by the statement after the one that sets it (lines 729-730), `TTUP-REVIEW-NEW-RECORD` ('V') is never set, and `TTUP-CHANGES-OKAYED-BUT-FAILED` ('F') is unreachable (COTRTUPC-028), so no row depends on them. "B with fetched values" and "B with blank old values" differ, because the program tests `TTUP-OLD-TTYP-TYPE` for blanks (lines 412-414, 1221-1225, 1280-1282).

### Endpoint mapping

The replacement server keeps no screen state. The screen keeps the state between requests, as the COMMAREA did, and the endpoints serve the steps that read or write the table or run a program edit:

- Endpoint 26 serves ENTER in the fresh and X states: the input store and key edits of `1000-PROCESS-INPUTS`, then the read of `2000-DECIDE-ACTION` → `9000-READ-TRANTYPE`.
- Endpoint 27, with `{type_code}` the code the screen shows:
  - `aid` ENTER serves ENTER in the S, E, B and R states: the edits of `1200-EDIT-MAP-INPUTS`, with no store effect.
  - `aid` PF5 serves F5 in state N: `9600-WRITE-PROCESSING`, an update, else an insert.
  - `aid` PF4 serves the second F4, in state 9: `9800-DELETE-PROCESSING`.
- No request: F3, F12, the first F4, F5 in state X, ENTER in state N, keys a state rejects, and every key after a completed save or delete. These rows are `client`: AAP 0.3.4.1 makes F3 and F12 client-side, and the first F4 and the X-state F5 change only the state and the prompt, which the screen holds.
- `aid` ENTER on endpoint 27 is a decision. AAP 0.3.4.1 names only PF5 and PF4 for endpoint 27, but the ENTER edits are program edits whose messages the server owns, so they run on the endpoint that carries `aid`, as endpoints 6 and 10 serve ENTER (validate) beside PF5 (save).
- On every endpoint 27 request the service re-reads the row to stand in for the COMMAREA. A row found means details were fetched: the key edits run and the comparison is with that row. No row means a new type: the key edits are skipped and the comparison is with blanks. X-COTRTUPC-2 lists where this can differ from the COMMAREA.

### Responses and status

- A success body carries the error row (`WS-RETURN-MSG`, empty when none) and the info row (`WS-INFO-MSG`, as `3250-SETUP-INFOMSG` sets it for the state the step leaves). An error response is a `ScreenError` whose `message` is the error row; the screen then sets the info row from the state the row names (COTRTUPC-045).
- 400: key, description and no-change edits, and an unserved `aid`. 401 and 403: the gate. 500: every store failure, which covers the fetch error, the lock error (Db2 `-911`), update and insert errors, the delete refused because categories exist (`-532`) and every other delete failure. Lock contention is a store failure, not a change by another user: the COBOL reports it with `Changes unsuccessful` and saves nothing.
- 404 is not used. A type no row holds starts the add path, and the response must return the normalised code that the screen shows and later sends to endpoint 27, which a `ScreenError` cannot carry, so it is a 200 `TranTypeView` with no description (COTRTUPC-010).
- 409 is never returned: `Record changed by some one else. Please review` is declared and tested but never set (COTRTUPC-025). No row uses the page-size status, since CTTU shows one record.
- PostgreSQL outcomes stand for the Db2 SQLCODEs the program tests: an `UPDATE` or `DELETE` that changes no row for `+100`; `foreign_key_violation` (SQLSTATE `23503`) on the delete for `-532`; `deadlock_detected` (`40P01`) or `lock_not_available` (`55P03`) on the update for `-911`; any other error for a negative SQLCODE.

### Text

- Literals are quoted exactly as the program moves them, trailing spaces included. `WS-RETURN-MSG PIC X(75)` reaches `ERRMSGO PIC X(78)`; `WS-INFO-MSG PIC X(40)` is centred into `WS-STRING-OUT PIC X(40)` and reaches `INFOMSGO PIC X(45)`. A `STRING … DELIMITED BY SIZE` into `WS-RETURN-MSG` stops at its 75th byte and overwrites every byte it reaches.
- `FUNCTION TRIM` removes leading and trailing spaces only, and returns a value of length zero for an all-space argument (IBM Enterprise COBOL for z/OS 6.4 Language Reference, "TRIM", as `online/COCRDUPC.md` cites it). The blank test and the character edit of the description rely on that (lines 858-859 and 882-885).
- The type code edit uses `FUNCTION TEST-NUMVAL` and `FUNCTION NUMVAL` (lines 934-955) with their language-defined argument syntax: optional leading and trailing spaces, at most one sign (a leading or trailing `+` or `-`, or a trailing `CR` or `DB`), and digits with at most one decimal point.

## How the rows are proved

- `server`: tests tagged `// audit: COTRTUPC-nnn` in `crates/api/tests/endpoints_transaction_types.rs`, against a migrated database, asserting status, message, field, response values and the contents of the `db2` tables. The store-failure rows use a repository double, which implements the same repository trait (AAP 0.5.4), returning the PostgreSQL error the row names; COTRTUPC-033 deletes a seeded type, all seven of which have categories.
- `client`: `frontend/src/screens/COTRTUP.test.tsx` (states, prompts, protection, keys and the abend screen), `frontend/src/lib/pfkeys.test.ts` (bindings) and `frontend/e2e/nav.spec.ts` (the F3 transfer and the entries from COADM01 and COTRTLI).
- `both`: the server half in `endpoints_transaction_types.rs`, the client half in `frontend/src/schemas/COTRTUP.test.ts`.
- The `HALTED(H3)` row carries its tags; its tests report `BLOCKED` and assert nothing.

## Rules governing this file

- Equivalence failure and H3 (E19): text Db2 defines asserts nothing; store effects, states and the program's own prefixes stay assertable.
- Behaviour constraint and R7 — Anomaly handling: the doubled `SQLERRM`, the trims, the stored length, the misreported failures and the abends are expected results; each anomaly is proposed after the table.
- Thin Request Handlers: the state rules belong to `domain::online::cotrtupc` and `api::services::cotrtupc`; the handlers only extract, call and map.
- Cardholder Data Redaction: no protected value passes through this program.
- R16 — Authority and protected paths: this file is the only one written; the COBOL is read in place.

- `X-COTRTUPC-1`
  - Found in: `cbl/COTRTUPC.cbl:652-661,694-707,716,1279-1284`.

  - Finding: in state X the code is editable, and ENTER with any non-blank code skips `1210-EDIT-TRANTYPE`. `1150-STORE-MAP-IN-NEW` either keeps the code (same code) or stores the trimmed input, after which the test at line 698 always holds, so the code is selected unedited and unnormalised.
