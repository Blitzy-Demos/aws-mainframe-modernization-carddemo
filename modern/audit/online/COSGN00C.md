# COSGN00C — sign-on (CC00)

This is the derive-lane (#2) audit of `app/cbl/COSGN00C.cbl` (260 lines), the sign-on program of transaction `CC00` and map `COSGN00` (`COSGN0A`). Its replacement is endpoint 1, `POST /api/v1/signon`, the only operation that requires no token: `SignonRequest` (user ID, password) → `SignonResponse` (`token`, user ID, user type, `next_route`), or `ScreenError { message, field }` with the HTTP status each row gives (AAP 0.3.4.1, 0.3.4.6). The screen is `modern/frontend/src/screens/COSGN00.tsx` at route `/signon`. The rows come before `crates/domain/src/online/cosgn00c.rs`, `crates/api/src/services/cosgn00c.rs`, `crates/api/src/handlers/cosgn00c.rs`, `crates/api/src/auth/{jwt,extract}.rs` and the tests that bind them. They also supply the frontend consumers: the screen `frontend/src/screens/COSGN00.tsx`, the session store `frontend/src/auth/session.ts`, the route guard `frontend/src/auth/RequireSignon.tsx` and the 401 session handling of `frontend/src/api/client.ts` (`COSGN00C-002`, `COSGN00C-004`, `COSGN00C-014` to `COSGN00C-017`, `COSGN00C-021`). `session.ts` and `RequireSignon.tsx` were first committed before this file; they were revalidated against its rows after it, and the 401 handling was corrected to `COSGN00C-021`, as the remedial sequence in `modern/audit/README.md` records. Code that consumes the rows is accepted only once this file is `Accepted` in the status table of `modern/audit/README.md` (a8, a9). The password is stored as typed and compared upper-cased (E26); that behaviour is preserved.

## Reading the table

- Rule ID: `COSGN00C-<nnn>`, numbered in program order from `001`; a row added later takes the next free number, so `COSGN00C-021` follows `COSGN00C-020`.
- Paragraph: the COSGN00C paragraph that holds the rule; `A → B` names the paragraph `A` performs.
- Input condition: the AID key or the request that reaches the paragraph, and the state that selects the branch. A field is blank when it is empty, omitted from the request, or all spaces: the 3270 counterparts are an unmodified field (`LOW-VALUES`) and a field of spaces.
- Expected result: the HTTP status, the message literal exactly as the program moves it, in single quotes with its spacing, and the field the error names, which is the field the program puts the cursor on (`MOVE -1 TO USERIDL` → `user_id`, `MOVE -1 TO PASSWDL` → `password`); then the store and identity effects. Outcomes are those of the sign-on service; how the handler maps them is not part of a row (Thin Request Handlers).
- Layer: `server` rows are observable through endpoint 1; `client` rows send no request. No row is `both`. The COSGN00 zod schema repeats only the map `LENGTH` of the two inputs, which `screens.md` audits as `both` (`COSGN00-027`, `COSGN00-031`); it repeats neither blank-field edit, so the program's messages reach the screen from the server unchanged.

## Escalation candidates

Proposed under R7 — Anomaly handling. The reviewer folds each candidate into `ESCALATIONS.md` under its next free ID, as its `## Later entries` section describes; until then the rows above cite the candidate names.

- `X-COSGN00C-1`
  - Found in: `app/cbl/COSGN00C.cbl:132-134,211-216`; `app/cbl/COUSR01C.cbl:154`.
  - Anomaly class: declaration-not-followed.
  - Finding: sign-on upper-cases the user ID and reads USRSEC by it, while COUSR01C stores the user ID as typed. A user added with a lower-case letter in the ID can therefore never be found; this is the user-ID counterpart of E26. No in-stream user ID holds one (`app/jcl/DUSRSECJ.jcl:35-44`).
  - Proposed resolution: preserved. Every sign-on of such a user gets `'User not found. Try again ...'` (`COSGN00C-019`); the key is never compared case-insensitively. The same case is proposed from the storing side as `X-COUSR01C-1` in `online/COUSR01C.md`; the two are folded into one escalation.
- `X-COSGN00C-2`
  - Found in: `app/cbl/COSGN00C.cbl:221-223,252-256`; `app/cpy/CSUSR01Y.cpy:21`.
  - Anomaly class: request-vs-repository.
  - Finding: the COBOL compares two 8-byte fields, a test that cannot fail to run. The replacement verifies against an argon2id PHC string (E25), which can fail for a reason other than a mismatch: a `password_hash` that does not parse or names unsupported parameters. No COBOL path corresponds.
  - Proposed resolution: treated as the `WHEN OTHER` branch of `READ-USER-SEC-FILE`: HTTP 500 `'Unable to verify the User ...'`, field `user_id`, no token (`COSGN00C-020`), with a tracing event that carries neither the hash nor the password. It is never reported as `'Wrong Password. Try again ...'`, which would invite retries of a credential that cannot verify. Not a parity result.
- `X-COSGN00C-3`
  - Found in: `app/bms/COSGN00.bms:156-160,175-180`; `app/cbl/COSGN00C.cbl:132-136`; `app/cpy/CSUSR01Y.cpy:18,21`.
  - Anomaly class: request-vs-repository.

- `X-COSGN00C-4`

  - Anomaly class: request-vs-repository.
  - Finding: a 3270 terminal runs one task at a time and stays locked until the task answers; `RETURN TRANSID(CC00)` hands the COMMAREA only to the next task of the same terminal, F3's `RETURN` without `TRANSID` and the menus' F3 transfer without a COMMAREA end the conversation, and each sign-on sets the identity afresh from its own USRSEC read. The browser sends requests asynchronously: a key-driven read is a mutation that leaving its screen does not cancel, so its answer can arrive after the user has pressed F3, reached sign-on and signed on again.   - Proposed resolution: `COSGN00C-021`. A 401 ends the stored session only when it answers a request sent with that session's token, or a request sent with no token while none is stored; the answer to a request of an earlier session, or to a token-less request arriving while a session is stored, changes neither the session nor the screen. The current session's 401 still ends it at once, before the body is read. Not a parity result.
